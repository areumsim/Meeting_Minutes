# 🤝 회의 비서 (Meeting Assistant) — 하나의 흐름

STT·요약·이메일을 하던 기존 코드에 **계획·사전 리서치·매칭/병합·일정 관리**를 얹어,
회의 생애주기 전체를 하나의 비서로 묶었습니다. 배치·실시간·웹·자동 감시 경로는 공통 모듈을
재사용하지만, 저장 위치와 병합 방식이 조금씩 다릅니다. 전체를 묶는 단일 명령은
root의 `run_meeting.py` / `run_meeting.bat`입니다.

## 생애주기

| 단계 | 하는 일 | 명령 | Cowork에 이렇게 말하면 됨 |
|---|---|---|---|
| 회의 전 | 계획 노트 안건 → 키워드·설명·관련 노트 자동 작성 | `prep` | "오늘 회의 준비해줘" |
| 회의 중 | 실시간 녹취(STT) | `record` / `realtime` | "회의 녹음 시작" |
| 회의 후 | STT→회의록→요약→액션→사실 검증→Wiki Context/Proposal→이메일 + 계획 매칭/병합 | `batch 파일` 또는 `process 파일` | "이 녹음 정리해줘" |
| 이후 정리 | 일정·충돌/이중예약·준비상태 점검 + 대시보드 | `schedule` / `status` | "이번 주 회의 정리/겹치는 거 있어?" |
| 이후 정리 | 매칭됐지만 보류된 녹음을 계획에 병합 | `merge` | "맞는지 확인하고 병합해줘" |
| 자동 수집 | 폴더에 들어온 오디오 안정화 후 처리 | `watch` / `ingest` | "새 녹음 자동 처리해줘" |
| 지식 검색 | Vault 인덱싱·Q&A | `reindex` / `ask` | "지난 회의 근거 찾아줘" |

## 매칭 방식 (회의 후)
- 같은 **날짜** + (**제목 유사** 또는 **비슷한 시간대 ±120분**)이면 계획 노트 후보.
  → 제목이 달라도 비슷한 시간에 한 회의면 잡습니다(미뤄진 회의 대응).
- **병합 전 반드시 사용자 확인**. 대화형(터미널)은 즉시 묻고, 비대화형(웹/자동)은
  새 노트로 두고 대시보드 **"🔗 병합 대기"** 에 띄운 뒤 Cowork에서 확인·병합합니다.
- 병합 시: 사전 내용 보존 + `## 회의 기록` 추가, status `planned→done`, 참석자 합집합.

## 명령 예시
```
run_meeting.bat                                      # 통합 메뉴
python run_meeting.py status                       # 현재 상태
python run_meeting.py prep                         # 다가오는 계획 회의 사전 리서치
python run_meeting.py batch 회의녹음.m4a --title "주간보고"     # 파일 처리(매칭/메일까지)
python run_meeting.py process 회의녹음.m4a --title "주간보고"   # 비서형 호환 명령
python run_meeting.py schedule --write-dashboard   # 일정/충돌 + 대시보드 갱신
python run_meeting.py merge                        # 병합 대기 확인 후 병합
python run_meeting.py realtime --topic "주간보고"   # 실시간 녹취
python run_meeting.py ingest 회의녹음.m4a --title "주간보고" --no-email
python run_meeting.py watch --folders "D:\Recordings"
python run_meeting.py reindex
python run_meeting.py ask "지난 회의 결정사항은?" --show-sources
```
(볼트 경로는 `--vault` 또는 `config.json → obsidian.vault_path`. `scripts/windows/run_assistant.bat` 는
인자 없이 실행하면 상태 요약, 인자를 주면 해당 명령 실행.)

QC 아카이브 기준 볼트는 `D:\Claude\QC`이며, 새 회의록 정식 저장 폴더는
`도메인_아카이브/01_회의_세미나/회의별`입니다. 실제 설정은 `python run_meeting.py obsidian --where`로 확인합니다.

기존 개별 bat는 호환용입니다. 새 작업은 `run_meeting.bat`에서 시작하는 것을 권장합니다.

## 처리 경로 선택

| 상황 | 권장 명령 | 결과 |
|---|---|---|
| 일반 녹음/영상 파일을 수동 처리 | `batch 파일` | `meeting_minutes.py` 경로. `output/` 저장 + Obsidian 발행/계획 매칭 + 알림 |
| 비서형 호환 명령으로 파일 처리 | `process 파일` | 내부적으로 `meeting_minutes.py`를 호출하며 `--resume`, `--force-stt`, `--debug` 같은 batch 옵션 전달 가능 |
| 자동 감시 또는 단일 파일을 녹음 노트로 정리 | `ingest 파일` | `ingestion_pipeline.py` 경로. 관련 노트 링크 포함, Obsidian recording note 또는 `output/` fallback |
| Obsidian 노트 안에 임베드된 녹음 처리 | `vault-audio` | 녹음이 들어 있던 기존 노트에 바로 `## 회의 기록` 병합 |
| 마이크 실시간 녹취 | `record` / `realtime` | `run_realtime.py` 실행 후 종료 시 회의록/요약/사실검증/Wiki Context/Proposal 생성 |
| 폴더 자동 감시 | `watch` | 안정화된 새 오디오를 `ingest` 파이프라인으로 처리하고 상태 파일에 기록 |

## Obsidian Wiki 컨텍스트

- 배치 처리(`meeting_minutes.py`)와 자동 수집(`ingest`)은 STT가 끝난 뒤 발화 내용을 기준으로 Vault 인덱스와 Obsidian REST 검색을 수행합니다.
- 찾은 관련 노트 본문 일부는 회의록 생성 메모에 들어가며, 생성된 Obsidian 노트에도 관련 노트 링크로 남습니다.
- CLI 실시간과 서버 `/ws/realtime`은 종료 후 모인 세그먼트를 기준으로 같은 Wiki 컨텍스트를 한 번 주입하고, 사실검증과 Wiki Proposal까지 남깁니다.
- 웹/모바일 Recorder의 direct OpenAI 경로는 로컬 기기 저장 중심 경로라 Vault/Wiki/사실검증을 우회합니다. 운영 기록으로 남길 회의는 CLI 실시간 또는 서버 `/ws/realtime`을 사용하세요.
- Obsidian은 로컬 지식 Wiki입니다. 최신 인터넷 정보가 필요하면 `wiki.online_search_enabled=true`일 때 별도 웹 리서치 메모로 보완하며, Vault 근거와 구분해서 넣습니다.
- `wiki.claim_verify=true`이면 회의록 생성 후 Vault 근거와 비교해 `## 사실 검증`을 추가합니다. 각 항목은 판정, 신뢰도, 근거 노트를 포함합니다.
- 처리 결과 폴더의 `wiki_context.json`에는 관련 노트, 레지스트리 액션/결정, 추출 용어/엔티티, STT 재사용 여부와 품질 메타데이터가 남습니다. 관련 노트가 있으면 `wiki_proposal.md/json`도 함께 생성됩니다.
- Obsidian 회의록/전사 파일명은 회의 날짜 기준 `yymmdd 제목.md` 형식입니다. 예: `260627 260627_5.md`.
- Obsidian 검색/연결 실패는 회의록 생성을 중단하지 않습니다. 이 경우 `output/` 파일 생성은 유지되고 Wiki 컨텍스트만 생략됩니다.

## 추가된 매칭/연동 (최근)

### ① 참석자 → 화자 자동 매핑
계획 노트에 적어둔 참석자(직책 표기 포함, 예 "최민석(팀장)")를 화자 추론 힌트로 자동 주입.
녹음의 Speaker A/B…가 실제 이름으로 더 정확히 붙습니다. batch·실시간 둘 다 적용.

### ② 옵시디언 자체 녹음 → 그 노트에 병합  (`vault-audio`)
회의 노트 안에서 Obsidian 오디오 레코더로 녹음하면 `![[녹음.webm]]` 로 임베드됩니다.
임베드 링크가 "어느 회의인지"를 명시하므로 매칭 없이 그 노트에 바로 회의록을 병합합니다.
```
python run_meeting.py vault-audio --vault "D:\Claude\QC"              # 처리
python run_meeting.py vault-audio --vault "..." --dry-run                # 대상만 확인
```
처리한 오디오는 노트 frontmatter `audio_processed` 에 기록해 재처리하지 않습니다.

### ③ 인물/팀 레지스트리  (`people`)
참석자 "이름(직책)"을 이름·직책으로 분리해 `01_References/People/<이름>.md` 인물 노트를
만들고 직책/부서/회사를 기록합니다. 인물 노트의 dataview가 그 사람이 참석한 회의를 자동 수집.
```
python run_meeting.py people --vault "..." --add "최민석(팀장),정하윤 수석"   # 직접 추가
python run_meeting.py people --vault "..." --department "AX팀"                  # 회의에서 수집
```
팀 단위로 묶으려면 인물 노트의 `department`(부서/팀)를 채우면 됩니다.

## 참석자 통일 & 비중요 발언 정리 (최근)
- **참석자 통일**: 속성(frontmatter) `attendees`를 정답으로, 회의록 본문 "참석자"도 그 **실명으로 통일**.
  생성 단계에서 계획 참석자 명단을 회의록 LLM에 지침으로 줘서 "발언자 A/B" 대신 실명으로 나오게 함.
  (이미 만들어진 옛 회의록엔 소급 적용 안 됨)
- **비중요 발언 정리**: 인사·잡담·여담 등은 회의록에서 빼고 핵심 논의·결정·액션만 정리.
- **요약/회의록 분리**: `한눈에 보는 요약`은 결론·결정·리스크·다음 액션만 짧게 쓰고,
  본문 `회의록`은 안건별 상세 논의·근거·미정 사항을 남깁니다.

## 녹음 자동 처리 (워처)
`scripts/windows/run_plan_watcher.bat`(= `plan_watcher.py`)를 켜두면:
- 계획 노트에 안건 저장 → 사전 리서치 자동 작성
- **옵시디언으로 노트 안에서 녹음 → 끝나면(파일 안정화 후) 자동으로 STT·요약·정리해 그 노트에 병합**
끄려면 `--no-audio`. 안정화 대기 `--audio-min-age 6`(초).

별도 녹음 폴더를 감시하려면 `python run_meeting.py watch` 또는 `python run_meeting.py audio-watcher`를 사용합니다.
이 경로는 `data/processed_audio.json` 같은 상태 파일에 `done/skipped/failed`, 노트 경로, 오류를 기록해
중복 처리를 막습니다. 실패한 파일은 `python run_meeting.py audio-watcher --reprocess <파일>`로 상태를 초기화한 뒤 다시 처리합니다.
