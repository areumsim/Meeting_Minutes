# PRD — Natively 검토의 실적용 (동의 정책 · Reference Files · 로컬/BYOK 참조 아키텍처)

문서 버전: v0.1 (초안)
작성일: 2026-07-30
대상 제품: Meeting Minutes Generator (음성/영상 → 회의록·요약·사실검증·Wiki)
선행 문서: `docs/기술검토_Natively_20260730.md` (Natively 대조·채택/불채택 판단)
문서 목적: Natively 검토에서 **아직 제품화되지 않은 세 갈래**를, 우리 시스템의 실제 구조 위에
구체 요구사항으로 정의한다. 이미 적용된 오디오 입력 계층(`ceb5d92`)과 녹음 고지 한 줄(`0c28713`)은
전제로 두고 그 위에서만 확장한다.

## 0. 배경 — 왜 이 PRD인가

Natively는 로컬·BYOK 회의 어시스턴트라는 점에서 우리와 방향이 같지만, **탐지 불가 스텔스 모드**를
기능으로 내세운다는 점에서 정면으로 갈린다. 기술검토는 이 이중성을 두 개의 운영 안건으로 정리했다.

- **리스크**: 임직원이 탐지되지 않는 녹취 도구를 개인 판단으로 쓸 수 있고, 이는 참가자 동의·사내
  녹취 정책과 충돌한다.
- **기회**: 클라우드 SaaS 없이 사내 로컬·BYOK 구성으로 회의록 자동화를 만들 수 있다는 참조 아키텍처.

검토는 오디오 갭과 "녹음 고지 한 줄"까지만 손댔다. 이 PRD는 그 결론을 **제품 기능과 문서**로
끝까지 밀어붙인다. 핵심 포지셔닝은 하나다 — **우리 도구는 스텔스의 반대편에 선 "고지·동의를
전제로 한 정식 도구"다.**

### 이미 적용된 것 (재요구 금지 — 이 PRD의 기준선)

| 항목 | 상태 | 근거 |
|---|---|---|
| 시스템오디오+마이크 캡처 3택 | 적용됨 | `ceb5d92`, `Recorder.tsx` |
| 녹음 시작 전 화면 참석자 고지 한 줄 | 적용됨 | `0c28713` (`Recorder.tsx`) |
| 스텔스 모드 | **정면 불채택** | 검토 §스텔스 모드 |
| BYOK / OpenAI→Groq→faster-whisper 폴백 | 적용됨 | `config.json`, `llm_client.py` |

이 PRD는 위를 다시 만들지 않는다. 위 기준선 **위에서만** 세 갈래를 추가한다.

## 1. 목표 / 비목표

### 1.1 목표 (Goals)

- **G1 (리스크).** "고지 한 줄"을 넘어, 회의록 산출물 자체에 **녹취 사실·시각이 남는** 최소한의
  감사 흔적을 만든다. 스텔스의 반대 증거가 기록으로 남는다.
- **G2 (리스크).** 사내 AI 도구 가이드에 "회의 녹취·전사 도구는 사전 고지·승인 대상"이라는
  문구가 있는지 확인하고, 없으면 우리 도구 사용자용 1페이지 정책 안내를 제공한다.
- **G3 (기회).** Reference Files(PDF/PPTX/DOCX 회의 자료)를 위키 지식순환에 편입해, 현재
  그림자 사본 규칙 때문에 빠져 있는 회의 원문을 검색·prep-brief에서 쓰게 한다.
- **G4 (기회).** "클라우드 SaaS 없이 사내 로컬/BYOK로 회의록 자동화가 성립한다"를 우리 시스템
  기준으로 정리한 **참조 아키텍처 문서**를 만들어 대외/사내 안건 소재로 재사용한다.

### 1.2 비목표 (Non-Goals)

- 스텔스·탐지회피 관련 일체 (정면 불채택 — 재론하지 않는다).
- 매 회의 강제 동의 모달·전자서명·법적 동의 수집 시스템. (사내 툴 맥락상 과함 — 검토 `0c28713`
  커밋 메시지의 판단을 존중한다.)
- 화면·슬라이드 OCR (동의 이슈 + 난이도, 검토에서 불채택).
- 채널별 화자 분리 STT (비용 2배, 검토에서 불채택).
- 새 STT/LLM 벤더·Ollama·커스텀 엔드포인트 추가 (사내 대상 아님, 검토에서 확인).

## 2. 트랙 A — 동의·녹취 정책 기능화 (리스크 대응)

### 2.1 문제

현재 방어는 "녹음 시작 전 화면에 안내 한 줄"뿐이다(`0c28713`). 이는 **녹음하는 사람**에게만
잠깐 보이고, **산출물에는 아무 흔적이 없다.** 나중에 "이 회의록이 언제·어떤 도구로 녹취됐나"를
확인할 방법이 없다. 스텔스의 반대편에 서려면, 안내가 아니라 **기록**이 필요하다.

동시에, `0c28713` 커밋 판단(매번 확인 강제는 실익 없음, 설정 키·모달·footer 미도입)은 옳다.
그래서 이 트랙은 **강제 없는 자동 기록** 쪽으로만 간다.

### 2.2 요구사항

**FR-A1 (P0) 회의록 산출물에 녹취 출처 메타 자동 기록**
회의록/요약 파일 생성 시 frontmatter 또는 문서 말미에 한 블록을 자동 삽입한다:
녹취 방식(파일 업로드 / 실시간 / 폴더감시), 처리 시각, 사용 STT·LLM 모델, 도구 버전.
사용자 입력 0개 — 파이프라인이 이미 아는 값만 쓴다. 이것이 "몰래가 아니다"의 물증이 된다.
- 저장 위치는 기존 출력 구조를 따른다(`docs/출력_구조_저장경로_요약회의록.md` 준수).
- 기존 회의록 본문 포맷·프롬프트는 건드리지 않는다(메타 블록만 추가).

**FR-A2 (P1) 실시간 녹음 고지 안내의 문구·노출 조건 점검**
`0c28713`의 한 줄이 (a) 실시간 경로뿐 아니라 (b) 파일 업로드·폴더 감시 진입점에서도
"이 도구는 몰래 녹음용이 아니다"라는 취지가 최소 1회 노출되는지 확인. 미노출 경로가 있으면
같은 톤의 정적 안내 한 줄을 추가(모달·상시 배너 금지 — 검토 판단 유지).

**FR-A3 (P0) 사내 녹취 정책 문구 존재 확인 + 사용자 정책 안내 1페이지**
사내 AI 도구 가이드에 "회의 녹취·전사 도구는 사전 고지·승인 대상" 문구가 있는지 확인한다
(담당: AR). 결과와 무관하게, 우리 배포본에 딸려가는 짧은 사용 수칙 1페이지를 만든다:
"녹음 전 참석자에게 알리기 / 승인 필요 회의 구분 / 산출물의 녹취 메타 의미". `USER_GUIDE.md`
또는 배포 `사용법.txt`에 편입.

**FR-A4 (P2) 도구 정체성 명문화**
README 상단·앱 정보 화면에 한 문장: "이 도구는 참가자 고지·동의를 전제로 한 회의 기록
도구이며, 탐지 회피(스텔스) 기능을 의도적으로 제공하지 않는다." 스텔스 도구와의 차별점을
제품 정체성으로 고정한다.

### 2.3 명시적으로 하지 않는 것
- 매 회의 동의 체크박스·모달 강제 (`0c28713` 판단 유지).
- 참석자 명단 수집·서명. 우리는 참석자 개인정보를 새로 모으지 않는다.

## 3. 트랙 B — Reference Files 위키 인덱싱 (기회 대응)

### 3.1 문제

회의 자료(PDF/PPTX/DOCX)의 텍스트추출 그림자 사본(`foo.pdf.md` 등)은
`vault_indexer.py`의 그림자 사본 규칙(`_SHADOW_COPY_ORIGINAL_EXTS` = `.pptx/.ppt/.docx/.doc/
.xlsx/.xls/.pdf/.log/.html …`)에 의해 **인덱싱에서 제외**된다. 결과적으로 회의 원문 자료가
위키 검색·관련노트·prep-brief 지식순환에서 빠져 있다. Natively의 "Reference Files"에 해당하는 갭.

이 규칙 자체는 정당하다 — 이진 원본의 자동 텍스트덤프가 검색 인덱스를 오염시키던 과거 문제를
막는 장치다. 그래서 **규칙을 없애는 게 아니라, 회의 자료만 통제된 경로로 편입**해야 한다.

### 3.2 요구사항

**FR-B1 (P0) 판정 단일 소스 유지**
새 인덱싱 대상 편입은 반드시 `vault_indexer.iter_note_files()` / `_is_indexable_note()`를
경유한다. 별도 스캔 로직을 복제하지 않는다(복제 시 그래프 백필과 갈라진다 — CLAUDE.md 경고,
과거 실제 발생). graph_sync 백필도 같은 함수를 쓰므로 한 곳만 고치면 양쪽에 반영된다.

**FR-B2 (P0) 회의 자료 편입 방식 결정 (택1 → §6 오픈이슈)**
후보 A: `02_Sources/` 하위 회의 자료를 대상으로, 추출본을 **일반 노트(.md, 그림자 접미사 아님)**
로 생성해 자연히 인덱싱되게 한다. 후보 B: 그림자 사본을 유지하되 `indexing`에 "회의자료 화이트리스트
경로"를 두어 그 경로의 추출본만 인덱싱 예외로 편입한다. — 인덱스 오염 위험과 reindex 비용 트레이드오프.

**FR-B3 (P1) 추출 파이프라인**
PDF/PPTX/DOCX → 텍스트 추출(의존성: pypdf 등, 스킬 계층 재사용 검토) → 노트화. 추출 실패·빈
문서·스캔본(이미지 PDF)은 인덱싱하지 않고 로그만 남긴다(환각·잡음 유입 방지).

**FR-B4 (P0) 임베딩 비용·reindex 영향 고지**
편입은 임베딩 비용과 `reindex` 재빌드를 유발한다. 대량 편입 전 예상 청크 수·비용을 산출해
로그로 보이고, 월 지출한도(`cost.monthly_cap_usd`, 서버 강제)와 정합하게 동작한다.

**FR-B5 (P1) 정합성 재빌드 절차 준수**
편입 후 `python run_meeting.py reindex` + `scripts/graph_backfill.py`를 함께 돌려 위키 검색과
지식그래프 노드/엣지를 맞춘다(CLAUDE.md §3). 볼트 CLAUDE.md의 인바운드 링크·dataview 경로
영향은 없음(노트 신규 생성이므로), 단 그림자 규칙 변경 시 회귀 테스트 필수.

### 3.3 검증
- 회의 자료 1건(PDF/PPTX 각) 편입 → `wiki-ask`로 그 자료의 고유 문구가 검색되는지.
- 편입 전/후 `iter_note_files()` 반환 집합 diff가 의도한 파일만 늘었는지(그림자 사본 오편입 0).
- 기존 회귀 스위트(2026-07-30 기준 560 passed) 무손상.

## 4. 트랙 C — 로컬/BYOK 참조 아키텍처 문서화 (기회 대응)

### 4.1 문제

"클라우드 SaaS(Otter·Fireflies 등) 없이 사내 로컬/BYOK로 회의록 자동화가 된다"는 명제를 우리는
이미 **제품으로 증명**하고 있는데, 그걸 한 장으로 설명하는 문서가 없다. 대외/사내 안건화나 신규 팀
온보딩 때마다 매번 구두로 재구성한다.

### 4.2 요구사항

**FR-C1 (P0) 참조 아키텍처 1문서 작성** — `docs/참조아키텍처_로컬BYOK_회의록자동화.md`
아래를 우리 시스템 실제 구성으로 채운다:
- 데이터 경계: 오디오·회의록·인덱스가 로컬(리포/포터블 데이터 폴더)에 머문다. 외부로 나가는 것은
  STT·LLM API 호출 페이로드뿐이며 BYOK로 사용자 키를 쓴다(`api.*`, 환경변수 우선).
- BYOK/폴백 체인: OpenAI → Groq → faster-whisper(로컬 오프라인 최종 백업). 네트워크·API 없이도
  로컬 전사가 성립하는 경로(`stt.local_fallback`).
- 비용 통제: 월/파일 지출한도 서버 강제(`cost.*`), `common/pricing.py` 비용 산출.
- SaaS 대비 표: 데이터 위치·구독·키 소유·오프라인 가능 여부를 Otter/Fireflies/Natively와 대조.
- **로컬≠안전** 단서: Natively 사례를 근거로, 로컬 실행이 곧 정책 준수는 아니며 트랙 A의 고지·기록이
  함께 있어야 함을 명시(기술검토의 핵심 메시지).

**FR-C2 (P1) SETUP_NEW_TEAM 연결**
참조 아키텍처 문서에서 실제 셋업은 `docs/SETUP_NEW_TEAM.md`로 링크. 개념(왜)과 절차(어떻게)를 분리.

**FR-C3 (P2) 대외용 요약 슬라이드(선택)**
안건화 요청이 있을 때만, HANBIT 서식으로 3–5장 요약 덱 파생(별건).

### 4.3 비목표
- 실제 아키텍처 변경 0. 이 트랙은 **기존 구성의 문서화**이지 신규 개발이 아니다.
