# 화자 분리(speaker diarization) 도입 계획

## 현재 상태 / 문제

- 지금 STT 모델(`gpt-4o-mini-transcribe`)은 **화자 분리를 하지 않습니다.** 전사 결과 세그먼트의 `speaker` 값이 전부 비어 있음.
- 그래서 회의록의 `발언자 A~E`는 실제 구분이 아니라 요약 LLM의 **추정 인원수**일 뿐 → "누가 무슨 말 했는지" 데이터가 없어 실명 매핑 불가.
- 화자별 구분을 넣으려면 **diarization 단계**를 파이프라인에 추가해야 함.

## 선택지

### A. 로컬 오픈소스 — pyannote.audio (+ WhisperX) ★프라이버시 우선
- **장점**: 무료, 오디오가 회사 PC 밖으로 안 나감(회사 회의에 적합), 기존 자체 호스팅 철학과 일치.
- **필요**: HuggingFace 토큰 + `pyannote/speaker-diarization-3.1` 모델 라이선스 동의, `torch`·`pyannote.audio` 등 무거운 의존성. CPU로도 되지만 28분 오디오에 수 분~십수 분, GPU 있으면 빠름.
- **연동**: diarization으로 (시작~끝, 화자) 구간을 뽑고, 기존 OpenAI 전사 세그먼트를 타임스탬프로 정렬해 각 세그먼트에 화자 라벨 부여.

### B. 클라우드 API — Deepgram / AssemblyAI ★도입 난이도 낮음
- **장점**: 오디오 한 번 업로드로 **전사+화자 라벨**을 한꺼번에 받음. 코드 적고 빠름.
- **단점**: 분당 과금, 그리고 **회사 회의 음성을 외부 벤더로 전송** → 데이터 거버넌스 확인 필수(회사 정책상 불가일 수 있음). 새 API 키 발급 필요.
- **연동**: 이 경우 STT 자체를 이 API로 교체(전사+화자 동시 획득)하는 게 깔끔.

> ※ OpenAI(현재 사용 중)는 화자 분리 기능을 제공하지 않습니다.

## 권장 경로

회사 회의 음성이라 **프라이버시상 A(로컬 pyannote)** 를 권장. 다만 셋업 부담이 있으니,
효과를 빠르게 보고 싶으면 외부 전송이 허용되는 범위에서 B로 파일럿 후 A로 정착하는 것도 방법.

## 도입 시 필요한 것 (회원님 준비물)

- A 선택 시: HuggingFace 계정 토큰 + 모델 라이선스 동의 1회. (회사 PC에 torch 설치 용량 ~수 GB)
- B 선택 시: 외부 전송 가능 여부(회사 정책) 확인 + Deepgram 또는 AssemblyAI API 키.
