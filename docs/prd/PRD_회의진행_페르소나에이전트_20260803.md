## 리뷰 요약 (팀 리뷰용 TL;DR)

**무엇을** — 회의 실시간 전사 위에, 여러 관점의 "페르소나"(촉진자·서기·도메인전문가·팩트체커·악마의 변호인·주니어/시니어·비판자)가 **화면 옆에 무음 카드로** 개입해 놓친 논점·모호한 정의·사실 오류 후보를 짚는 보조 에이전트. 페르소나마다 **참견도 0(금지)~5(음성)**를 사용자가 조절.

**핵심 판단** — 인프라의 70%는 이미 있다(세그먼트 훅·옆 카드 스트리밍·볼트/웹 검색·비용 함수). 진짜 신규는 "회의 중 통제된 개입"이다. **v1 범위 = M0 관찰모드 + M1 앰비언트 옆 카드**로 한정. 음성·위험 페르소나·적극 개입은 실측 게이트 뒤로.

**리뷰어가 특히 볼 것 (냉철한 리스크)**

| # | 리스크 | 문서 위치 | 리뷰 판단 필요 |
|---|---|---|---|
| R1 | 실시간 경로가 **현재 비용 무계량**(realtime.py에 spend_guard 0건). 새 상시 호출이 같은 함정에 빠지기 쉬움 | §10, 부록 B | 계량 배선을 착수 게이트로 못박을지 |
| R2 | 팩트체커가 회사망 차단 시 **검증 없이 사실확인처럼** 응답 | §6 | `searched=True` 게이트를 필수로 둘지 |
| R3 | 회의 중 AI 개입은 **업계에서 반발**(MS Teams 2026 토글 사태). 통제·기본 절제가 정답 | §18 | 사내 정책·참석자 고지 필요 여부 |
| R4 | 회의 중 지적은 **오전사 조각**을 붙잡을 수 있어 종료 후보다 부정확 | §17①, §15 | 위험 페르소나 오탐률 실측 기준치 |
| R5 | 음성 되먹임 방지 **미구현·코드로 증명 불가** | §11 | 음성을 v1에서 뺄지(권고: 뺌) |

**리뷰어 결정 요청** — §16(미결)에 5건. **UI/UX 상세는 §19**, 실현가능성·업계 판정은 §17·§18, 코드 근거는 부록 B.

**착수 규모** — M0 3~4 MD, M1 2~3 MD, UI 포함. 나머지 단계는 실측 게이트 통과 후 산정(§13).

## 0. 요청과 그 해석

> "음성을 달고, 실시간 검색을 켜서, **참견도를 수치로 받아**(금지 포함) 의견을 내는 **페르소나 여러 개**를 두자. 사용자가 생각 못 한 질문을 먼저 제안하고, 잘못된 의견·모호한 질문·대화 중 놓친 부분을 짚어 회의를 제대로 이끄는 에이전트."

요청을 분해하면 **다섯 개의 독립 기능**이다. 묶어서 판단하면 안 된다 — 위험·난이도·비용이 다르다.

| # | 기능 | 담당 페르소나 | 위험 | 선행 문서 |
|---|---|---|---|---|
| ① | **잘못된 의견 지적** (사실 오류·모순·논리 비약) | 팩트체커, 비판자, 악마의 변호인 | **높음**(사회적·정확성) | 음성브리핑 트랙 B(보류) |
| ② | **모호한 질문/미정의 용어 짚기** | 질문자(주니어) | 중간 | 신규 |
| ③ | **놓친 부분 체크** (미결 논점·오너 없는 결정) | 서기, 촉진자 | 낮음 | 음성브리핑 트랙 A와 인접 |
| ④ | **사용자가 생각 못 한 질문 선제안** | 도메인 전문가, 시니어(redteam) | 중간 | 신규 |
| ⑤ | **참견도 수치 제어 + 음성 출력** | (공통 제어층) | 중간 | 음성브리핑 트랙 C(음성) |

**핵심 판단**: ③은 이미 준비된 인프라 위에서 낮은 위험으로 가능하다. ①·④는 가치가 크지만 **틀린 개입의 사회적 비용이 비대칭**이라(발언자를 회의 중 공개 오정정) 반드시 관찰모드 → 실측 → 점진 개방 순서를 밟는다. 이 순서를 "참견도"라는 하나의 수치축으로 통합하는 것이 이 PRD의 설계 골자다.

## 2. 목표 / 비목표

**목표**
- 긴 회의에서 참석자가 놓치기 쉬운 것(미결 논점, 오너 없는 결정, 모호한 정의, 사실 오류 후보, 검토 안 된 대안)을 **적시에, 통제된 강도로** 드러낸다.
- 각 관점을 **독립 페르소나**로 두고, 페르소나별 **참견도(0=금지 ~ 5=최대)**로 사용자가 개입 빈도·채널을 직접 조절한다.
- 개입의 **틀림**이 만드는 사회적 비용을 구조적으로 억제한다(대조 표현 한정, 화자 비귀속, 관찰모드 선행, 오탐률 실측 게이팅).
- 비용·자동 실행·프라이버시에서 기존 안전장치를 **우회하지 않는다**.

**비목표(명시적으로 하지 않는다)**
- 회의 진행자 대체(발언권 통제, 참석자 평가·채점).
- **화자 귀속 지적**("A 님 말이 틀렸다"). 개입은 항상 "내용"에 대한 것이고 "누가"를 결부하지 않는다.
- 회의록 승격. 개입은 전부 "초안/보조" 라벨이며 finalize 회의록의 사실 검증을 대체하지 않는다.
- 실시간 화자분리 개선(별건, 배치 후처리로 이미 결정됨).
- 외국어 실시간 통역.

## 3. 페르소나 로스터

페르소나는 **역할·트리거·출력·기본 참견도·채널·모델 티어**로 정의된다. 사용자가 확정한 필수/강조를 반영했다.

| 페르소나 | 역할 | 주 트리거 | 근거 소스 | 기본 참견도 | 위험 |
|---|---|---|---|---|---|
| 🧭 **촉진자** (Facilitator) | 회의 흐름 관리 — 주제 이탈, 시간 초과, 결론 없이 다음으로 넘어감 | 논점 전환·장시간 미결 | 대화 내부 | **3 표준** | 낮음 |
| 📝 **서기** (Scribe) | 놓친 부분 체크 — 오너/기한 없는 결정, 제기됐지만 답 없는 질문, 미결 액션 | 결정·액션·질문 발화 | 대화 내부 | **3 표준** | 낮음 |
| 🎓 **도메인 전문가** (Domain Expert) *(필수)* | 사내 지식 기반 전문 반박·보강, 선제 질문 | 도메인 용어·기술 주장 | **볼트 RAG** + 웹 | **2 소극** | 중간 |
| 🔍 **팩트체커** (Fact-Checker) *(강조)* | 사실 오류 후보 대조 — 수치·날짜·인용·고유명사 | 검증 가능한 단정 | **웹 검색** + 볼트 | **2 소극** | 높음 |
| 😈 **악마의 변호인** (Devil's Advocate) *(강조)* | 집단사고 차단 — 합의에 의도적 반대, 검토 안 된 대안·리스크 제기 | 빠른 합의·낙관 단정 | 대화 내부 + 볼트 | **2 소극** | 중간 |
| 🐣 **주니어** (Junior / redteam) | 모호한 질문·미정의 용어를 "초심자 시점"으로 질문 | 정의 없는 약어·모호 지시대명사 | 대화 내부 | **2 소극** | 낮음 |
| 🧨 **시니어** (Senior / redteam) | 선제 질문 — "이거 물어봤어야 하지 않나", 숨은 가정·실패 모드 | 계획·결정 발화 | 볼트 + 대화 | **1 관찰** | 중간 |
| 🧐 **비판자** (Critic) | 논리 비약·근거 없는 단정·앞말과의 모순 지적 | 인과·일반화 주장 | 대화 내부 | **1 관찰** | **높음** |

설계 원칙 `[설계 판단]`:
- **위험이 높은 페르소나일수록 기본 참견도가 낮다.** 팩트체커·악마의 변호인은 강조 대상이지만 기본 2(소극), 비판자는 기본 1(관찰). 사용자가 신뢰가 쌓인 뒤 올린다.
- **필수(도메인 전문가)는 끌 수 있되 기본 켜짐(2)**. 사내 볼트라는 이 시스템만의 강점을 활용하는 페르소나여서 기본 노출한다.
- 페르소나는 **프롬프트 프로파일**이다(별도 모델 아님). 시스템 프롬프트·트리거 규칙·출력 스키마만 다르고, 모델 티어는 §5에서 배정한다.

## 4. 참견도(Intervention Level) 수치 체계 — 이 PRD의 제어 골자

사용자 요청의 "참견도를 수치로, 조정·금지 가능"을 **0~5 정수축**으로 구현한다. 페르소나마다 독립값이고, 그 위에 **전역 상한**이 있다.

| 값 | 이름 | 동작 | 채널 | 개입 빈도 상한 |
|---|---|---|---|---|
| **0** | **금지** | 그 페르소나를 아예 돌리지 않는다(트리아지 대상에서 제외 → 비용 0) | 없음 | 0 |
| **1** | **관찰(silent)** | 내부적으로 판정·로깅만. 화면에 **절대 안 뜬다**. **오탐률 실측 전용 모드** | 로그(DB)만 | 무제한(비표시) |
| **2** | **소극** | 사용자가 [지금 점검] 버튼을 누를 때, 또는 세그먼트 구간 종료 시 접이식 카드로 **모아서** 표시 | 화면 카드(수동/저빈도) | 세션당 소수 |
| **3** | **표준** | 의미 있는 트리거 발생 시 화면 카드로 표시(스로틀). 소리 없음 | 화면 카드 | interval 게이트 |
| **4** | **적극** | 표준 + 중요 개입 시 **알림음** + 배지 강조 | 화면 카드 + 알림음 | interval 게이트(짧게) |
| **5** | **최대** | 적극 + **음성 낭독** + **선제 질문 제안** 활성 — **v1 제외, M3 파일럿에서만**(§11: 되먹임 방지 미구현·미검증) | + 음성(speechSynthesis) | interval 게이트(짧게) |

핵심 규칙 `[설계 판단]`:
- **금지(0)는 진짜 0 비용.** 트리아지 프롬프트에서 그 페르소나 항목을 제거한다. 회귀 테스트로 "0인 페르소나는 LLM 입력에 등장하지 않음"을 고정한다.
- **관찰(1)은 실측을 위한 1등석 좌석이다.** 회의 중 판정을 DB에 남기되 화면엔 안 띄우고, 종료 후 finalize 사실검증(전량·2단계 보정 후)과 대조해 **페르소나별 오탐률**을 계산한다. 이 수치 없이 위험 페르소나를 2 이상으로 올리지 않는다(§15).
- **전역 상한(`facilitation.max_level`)**: 개별 페르소나 값이 아무리 높아도 이 값을 넘지 못한다. 사내 배포 기본 3. 관리자가 4·5를 열어야 음성/알림음이 가능.
- **전역 개입 예산**: 세션당 표시 개입 총량 상한(`facilitation.max_interventions_per_session`, 기본 12). 초과하면 이후 개입은 관찰(로그)로 강등 — 회의를 시끄럽게 만들지 않는다.
- **위험 페르소나 상한 캡**: 비판자·팩트체커는 `max_level`과 별개로 코드상 **하드 캡**(예: 실측 전 최대 2)을 둔다. 설정만으로 위험 개입을 열 수 없게 한다.

## 5. 하이브리드 계층형 모델 파이프라인 (사용자 확정)

상시 실시간 호출의 비용을 억제하는 2단(triage → generate) 구조. **경량 모델이 매 세그먼트를 훑고, 상위 모델은 실제 개입을 만들 때만 부른다.** `[설계 판단]`

```
STT 세그먼트 확정 (realtime.py 핫패스)
  └─ FacilitationOrchestrator.offer_segment(text)   ← RealtimeVaultSearcher 와 동일 계약
       · 논블로킹 / raise 금지 / 스레드풀 / interval·내용 게이트
       │
       ├─ [Tier 0 · 트리아지]  경량 모델 1회 (haiku / gpt-4o-mini)
       │     입력: 최근 창(window) + 활성 페르소나(참견도>0) 목록 + 이전 요약 1개
       │     출력(JSON): [{persona, trigger_type, confidence, span, need_search}] 후보만
       │     · 게이트: spend_guard.blocked() → automation_paused()
       │
       ├─ 후보 필터: confidence ≥ 페르소나 임계 && 참견도 채널 충족 && 전역 예산 잔여
       │
       └─ [Tier 1 · 생성]  후보가 있을 때만, 페르소나별 상위 모델
             · need_search 이면 먼저 근거 수집:
                 - 볼트: RealtimeVaultSearcher.collected_evidence()  (이미 상시 수집 중)
                 - 웹:  LLMClient.web_research(query)   (팩트체커/도메인, 게이팅 하)
             · 개입 문장 생성(대조 표현·화자 비귀속·"초안" 라벨)
             └─ WS {"type":"facilitation", persona, level, kind, text, evidence[], span}
                   └─ 프런트: 페르소나 카드 (+참견도 4↑ 알림음, 5 음성 낭독)
```

**모델 배정(기본값, 설정 override 가능)** `[설계 판단]`:

| 단계 | 역할 | 기본 모델 | 근거 |
|---|---|---|---|
| Tier 0 트리아지 | 매 세그먼트 후보 판정(상시) | `claude-haiku-4-5` 또는 `gpt-4o-mini` | 저단가·빠름. 회의 1시간 상시 호출의 비용 결정 요인 |
| Tier 1 · 촉진자/서기/주니어 | 흐름·놓침·모호성 (판정 쉬움) | `gpt-4o-mini` / `claude-haiku-4-5` | 비용↓, 품질 충분 |
| Tier 1 · 도메인/시니어/악마의 변호인 | 전문 추론·대안 제시 | `claude-sonnet-5` | 추론·균형 |
| Tier 1 · 팩트체커/비판자 | 오류·모순 판정(오탐 비용 큼) | `claude-opus-4-8` (+ `web_research`) | 정확도 최우선. 저빈도라 총비용 관리 가능 |

- 모델 문자열은 기존 config 옵션과 동일(`config_schema.py`의 `models.claude_model`/`gpt_model` 옵션에 존재): `claude-opus-4-8`, `claude-sonnet-5`, `claude-haiku-4-5`, `gpt-4o`, `gpt-4o-mini`. `[소스 검증]`
- LLM 호출은 전부 `common/llm_client.LLMClient.chat(system, user, temp, model, max_tokens)` 경유(SSL·키·reload 훅이 이미 붙어 있다). **동기 호출**이므로 반드시 스레드풀에서 실행 — 이벤트 루프에서 부르지 않는다. `[소스 검증]`
- 트리아지는 페르소나별로 나누지 않고 **1회 호출에 활성 페르소나 전부**를 묶어 판정한다(호출 수는 페르소나 수와 무관).
- **트리아지는 세그먼트 수가 아니라 시간 기반으로 돈다**(`triage_period_sec`, 기본 25초). 정정 근거: 세그먼트는 `realtime.fast_max_chunk_sec=5s` 기준 시간당 최대 ~700개까지 날 수 있어(`realtime.py:911`), "N 세그먼트마다"로 잡으면 상한이 발화량에 휘둘려 비용을 예측할 수 없다. 시간 기반이면 1시간 회의 = 최대 ~144회로 고정된다. `[소스 검증]`
- **전용 스레드풀을 새로 둔다.** 기존 `_web_pool`은 `max_workers=1`이라(`realtime.py:183`) 웹검색만으로도 병목이다 — 트리아지를 여기 얹으면 관련노트·웹 표시가 뒤로 밀린다. 오케스트레이터는 자체 풀(`max_workers=2`)을 갖는다. `[소스 검증]`

## 6. 실시간 검색 연동 (요청 "실시간 검색 활성화")

두 소스를 **볼트 우선, 웹 보완**으로 쓴다. 새 검색기를 만들지 않고 기존 것을 재사용한다.

- **내부(볼트)**: `RealtimeVaultSearcher`가 이미 상시 `offer_segment`로 근거를 모으고 있다. 페르소나는 `collected_evidence(limit, min_rank_score)`로 그 결과를 가져다 쓴다 — 추가 검색 호출 0. `[소스 검증]`
- **외부(웹)**: 팩트체커·도메인 전문가만, `need_search=true` 후보에 한해 `LLMClient.web_research(query)` 호출. `_maybe_web_research`의 게이팅을 그대로 따른다: `wiki.online_search_enabled` && `facilitation.web_search_enabled` && 볼트 히트 없을 때 우선(`realtime_web_only_if_no_vault_hit` 정신). `[소스 검증]`
- 웹 검색은 **회의 1건당 십수 회 호출**되면 비용·지연이 커진다(llm_client 주석의 경고). 그래서 팩트체커 참견도 + `facilitation.web_search_interval` 이중 게이트를 둔다. `[소스 검증 근거의 설계 확장]`
- 근거가 붙은 개입만 팩트체커/도메인 채널로 내보낸다. 근거 없으면 개입을 만들지 않는다("추측 금지"는 web_research 시스템 프롬프트에도 이미 명시).
- **팩트체커는 `web_research`가 `searched=True`를 돌려줄 때만 개입한다(필수 게이트, v0.2 신설).** `web_research`는 3단 폴백으로, 회사망 차단·크레딧 소진·`_anthropic_web_disabled` sticky 상태에선 **라이브 검색 없이 `searched=False`(모델 파라미터 지식)로 조용히 강등**된다(`llm_client.py:311·348·397·416`). 이때 개입하면 검증되지 않은 모델 추정을 "사실확인"처럼 권위 있게 내놓는 것이라 없느니만 못하다. 따라서 (a) `searched=False`면 팩트체커 개입을 억제하고, (b) 카드에 `searched` 배지("🌐 라이브 검증" vs "⚠ 미검증")를 노출해 사용자가 신뢰 수준을 구분하게 한다. `[소스 검증]`

## 10. 비용 설계 (우회 금지 — CLAUDE.md 3대 단일 소스)

**⚠ v0.2 정정 — "가드 가능"은 조건부다.** 감사 결과: `web/backend/api/realtime.py` 전체에 `spend_guard` 참조가 **0건**이다. 즉 기존 실시간 웹검색(`_web_research_segment`→`llm.web_research`)조차 지금 `blocked()` 게이트도 `record()` 기록도 없이 돈다 — 실시간 웹검색 비용은 현재 월 합계에서 안 보인다. `spend_guard.py` 독스트링 스스로 "재생성·폴더감시·계획자동화가 검사를 통째로 비켜갔다"고 적고, git 로그에도 같은 계열 수정이 반복된다(`38224d0` 실시간 STT가 요청 한도를 통째로 우회 / `6e96524` 임베딩 과금이 한도 밖 / `8116e7a` 자동실행에 한도 적용). **이 리포에서 상시·자동 경로가 가드를 우회하는 것은 예외가 아니라 반복된 실패 양상이다.**

따라서 **"복제하면 된다"가 아니라 "새로 배선해야 하고, 배선을 빠뜨리기 가장 쉬운 지점"**으로 다룬다. 신규 경로는 반드시 아래를 지난다. `[소스 검증 — grep spend_guard realtime.py = 0]`

- **추정**: `pricing.estimate_session_cost()`에 트리아지 횟수·개입 횟수·웹검색 횟수를 반영하는 항을 추가한다. 예상 비용 모달의 금액과 실제 한도 판정이 **같은 함수**에서 나와야 한다(CLAUDE.md). 단가 표를 직접 `.get`하지 않고 `LLM_TOKEN_PRICE` 헬퍼를 쓴다.
- **기본 설정에선 `blocked()`가 무력하다는 점을 직시한다.** `cost.monthly_cap_usd`·`per_file_cap_usd` 기본값이 0(무제한)이고 `blocked()`는 fail-open(판정 실패 시 통과)이다(`spend_guard.py:59·63`). 신규 설치에선 사실상 아무것도 안 막는다. 그래서 이 기능 **전용 상한 `max_cost_usd_per_meeting`을 spend_guard와 별개로 신규 구현**하고, 세션 내 누적치를 오케스트레이터가 직접 들고 매 개입 전에 검사한다(전역 캡 0이어도 동작). `[소스 검증]`
- **한도**: 매 트리아지·매 개입 전에 `spend_guard.blocked(est)`. 막히면 **조용히 건너뛰지 않고** 화면에 "지출 한도로 개입 보류"를 남긴다(CLAUDE.md: 조용히 꺼지면 기능이 없는 것처럼 보인다). 여기에 더해 이 기능 전용 상한 `facilitation.max_cost_usd_per_meeting`을 별도 검사.
- **집계**: 세션 있으면 `db.add_session_cost()`(누적), 세션 없는 경로는 `spend_guard.record(kind=KIND_FACILITATION, cost_usd=…, model=…, note=…)` → `usage_log` → `month_to_date_spend()`에 잡힌다. `update_session_status`는 덮어쓰기라 부적합. `[소스 검증]`
- **자동 실행 관문**: `automation_paused()`(전역 일시정지)도 지난다 — 상시 트리아지는 사실상 자동 실행이다.

**개략 비용 추정** `[미검증 — 실측 필요]`: 1시간 회의, 트리아지 2세그먼트 간격(≈150회), 회당 입력 ~1.5k·출력 ~150 토큰, haiku 기준 트리아지 총 **~$0.05**. 실제 개입 12회(Opus/Sonnet 혼합, 근거 포함 입력 ~3k·출력 ~300) **~$0.15**. 웹검색 6회 **~$0.05**. **세션당 ~$0.25 수준**. 회의록 생성 1회(`MINUTES_COST_PER_SESSION` ≈ $0.08)의 약 3배 — 그래서 `max_cost_usd_per_meeting` 기본 $0.50 캡을 둔다.

## 11. 개입 채널 스펙트럼 — 옆 멘트(앰비언트)가 v1의 핵심 가치, 음성은 뒤로

**중요한 재정렬(v0.2).** 이 기능의 가치는 "얼마나 세게 끼어드느냐"가 아니라 **"논의가 살아있는 그 순간에, 옆에서, 의견을 보완해 주느냐"**에 있다. 음성이 아니어도 — 화면 옆에 페르소나 멘트가 **흘깃 보이는 것(glanceable)만으로도** 참석자의 생각이 보강되고 놓친 질문이 떠오른다. 이게 v1의 본체다. 채널을 세 단계로 분리한다.

| 채널 | 인지 부하 | 방해도 | v1 | 근거 |
|---|---|---|---|---|
| **① 앰비언트 옆 카드** (glanceable, 무음, 참견도 2~3) | 낮음 | 낮음 | **핵심 · 포함** | `related_notes`가 이미 같은 방식으로 옆 카드 스트리밍(`Recorder.tsx:530`). 인프라 실재 |
| **② 알림음 + 배지 강조** (참견도 4) | 중간 | 중간 | 포함(전역 상한 개방 시) | 중요 개입만 |
| **③ 음성 낭독** (참견도 5) | 높음 | 높음 | **제외 → M3 파일럿** | 되먹임 방지 미구현·미검증 |

**왜 앰비언트가 실시간에 딱 맞나 `[소스 검증 + 업계 근거]`**: 화면 옆 카드는 이미 이 시스템이 회의 중 관련 노트를 띄우는 바로 그 채널이다(`_emit_related_notes`→WS `related_notes`→`Recorder.tsx:530`). 페르소나 개입은 **같은 자리에 카드 한 장을 더 얹는 것**이라 신규 UI 위험이 거의 없다. 그리고 CHI 2025 연구(§18)는 "능동 토론 중에는 짧은 요약이 방해를 최소화한다"고 못박는다 — 옆 카드·짧은 문장·무음이 정확히 그 처방이다. 실시간성이 중요한 이유도 여기 있다: **보완은 그 주제가 살아있을 때만 쓸모가 있다.** 10분 뒤에 "아까 그건 모호했어요"는 회의록의 몫이지 실시간의 몫이 아니다(그래서 서기·촉진자는 실시간, 상세 검증은 종료 후 finalize로 역할을 나눈다).

**음성(③) — v1 제외, 그러나 폐기 아님.** 사용자가 지적하듯 실시간 음성 개입도 가치가 있다. 다만 지금은 (a) 프런트에 `speechSynthesis`가 한 줄도 없고(`test/setup.ts` 주석: "아직 쓰지 않지만 PRD 검토 단계"), (b) 스피커→마이크 되먹임을 막는 STT 업스트림 중단이 코드에 없다(재생 중 마이크 track 제어 부재). 되먹임은 코드로 증명 불가능하고 실기로만 검증된다. 그래서 M3 파일럿(헤드셋 전제, 되먹임 실측)에서만 연다 — 엔진은 브라우저 `speechSynthesis`(비용 0·외부 전송 0, 배포 CSP `connect-src 'self'` 승계), 개입 1건당 3문장 상한, [즉시 정지], 한국어 OS 음성 부재 시 화면 폴백. `[소스 검증]`

**선제 질문 제안(요청 ④)**은 음성과 분리한다 — 참견도 3(앰비언트 카드)부터 도메인 전문가·시니어가 "이건 물어봤어야 하지 않나: …"를 카드로 낸다(`kind=question`, `draft=true`). 음성 없이도 v1에서 동작하는 핵심 가치다.

## 14. 수용 기준

- 기본 설정(`facilitation.enabled=false`)에서 이 기능이 **한 번도 호출되지 않는다**(LLM 모킹 회귀 테스트로 고정).
- 참견도 **0인 페르소나는 트리아지 입력에 등장하지 않는다**(비용 0, 테스트 고정).
- 참견도 **1(관찰)에서 화면 이벤트 0건**, DB 관찰 로그만 증가.
- 침묵 20분 → 트리아지·개입 0회(내용 게이트).
- `spend_guard.blocked()` 또는 `max_cost_usd_per_meeting` 초과 시 개입 0회 + 화면 사유 표시.
- 위험 페르소나(팩트체커·비판자)는 설정만으로 `hard_cap` 초과 참견도로 올릴 수 없다.
  (2026-08-05: `hard_cap` 을 2→3 으로 열었다 — 기본값은 1(관찰) 유지. §22.2 참조)
- 전역 개입 예산 초과 후의 후보는 관찰로 강등(화면 미표시).
- 예상 비용 모달 금액이 트리아지·개입·웹검색 횟수를 반영(표시=판정 동일 함수).
- 모든 개입에 `draft=true`, 화자 이름 미포함, `kind=contrast`에 판정 문구 없음.
- **(v0.2) 계량 검증**: facilitation 호출 1건 후 `usage_log.month_to_date_by_kind()['facilitation']`가 증가한다(무계량 회귀 방지 — 이 리포의 반복 결함을 테스트로 고정).

## 17. 실현가능성 냉철 검토 (현재 코드 기준, 2026-08-03 감사) `[소스 검증]`

기준 커밋: HEAD `38cbcb2`. 네 축으로 정직하게 판정한다.

**① 현재 코드 기반으로 실 의미 있는가 — 그렇다(구조 70% 존재), 단 정확도엔 구조적 한계.**
세그먼트 확정 핫패스(`realtime.py:1156` `offer_segment`, `:1159` `_maybe_web_research`), 스레드→async 푸시 큐(`_send_to_browser`), 볼트 검색기, 옆 카드 스트리밍(`related_notes`)이 모두 실재한다. 페르소나 오케스트레이터는 이 위에 카드 한 장을 더 얹는 구조여서 자연스럽다. **한계**: 세그먼트는 `provisional:true`(2단계 보정 전 조각 전사)로 먼저 나가고 revise가 나중에 교체한다(`realtime.py:1147`). 회의 중 지적은 오전사 조각을 붙잡을 수 있어 종료 후 검증보다 구조적으로 부정확하다 — M0 관찰모드·오탐률 게이트의 근거가 강화된다.

**② 프로덕션 수준으로 도움 되는가 — 앰비언트 페르소나는 예, 팩트체커는 조건부.**
촉진자·서기·주니어·시니어·악마의 변호인은 외부 검색에 의존하지 않아 프로덕션에서 바로 유효하다. 반면 팩트체커의 `web_research`는 회사망 차단·크레딧 소진 시 `searched=False`로 조용히 강등되고 sticky로 꺼진다(`llm_client.py:311·353`). 검증 없는 모델 추정을 사실확인처럼 내놓는 리스크 → §6의 `searched=True` 게이트가 없으면 프로덕션 부적합.

**③ 실시간 음성이 도움 되는가 — 가치는 있으나 지금은 미검증. 실시간 "옆 멘트"가 실제 v1 가치(§11·§18).**
음성 자체는 미구현(`speechSynthesis` 0줄)이고 되먹임 방지가 없어 실기 검증 전엔 못 켠다. 그러나 실시간성의 가치는 음성에 있지 않다 — **옆에 뜨는 무음 카드만으로 의견이 보완되는 것**이 핵심이며, 그 채널은 이미 작동한다. 음성은 M3로 미루되 실시간 가치는 v1에서 온전히 실현된다.

**④ 비용 가드가 가능한가 / 가드레일이 유의미한가 — 함수는 옳으나 "자동으로 되는" 게 아니다.**
`realtime.py`에 `spend_guard` 참조 0건 → 기존 실시간 웹검색조차 무계량(§10). 가드는 **직접 배선해야 하고, 이 리포에서 반복적으로 누락돼온 바로 그 지점**이다. 기본 설정(cap=0)에선 `blocked()`가 무력하므로 전용 `max_cost_usd_per_meeting`을 신규 구현해야 한다. 나머지 가드레일(대조표현·화자 비귀속·하드캡·관찰모드·오탐률 게이트·전역 개입 예산)은 코드로 강제 가능하고 유의미하다. `_web_pool`이 `max_workers=1`이라(`realtime.py:183`) 전용 풀 신설이 필수.

**종합 판정**: 방향 유효, 인프라 상당 부분 존재. 단 (a) 음성 v1 제외, (b) 팩트체커 searched 게이트 필수, (c) 비용은 "가능"이 아니라 "직접 배선+테스트 고정 필수". **M0 관찰모드 → M1 앰비언트 옆 카드**가 위험 대비 가치가 가장 높은 착수 경로다.

## 18. 업계 동향 대비 의미 — 냉철한 판정 `[웹 검색 2026-08]`

**결론부터: 이 설계는 업계가 2026년에 도달한 합의(강한 개입은 반발, 통제 가능한 앰비언트가 정답)와 정확히 같은 방향이다. 단 "실시간 개입 자체가 신선한 가치"라는 기대는 접어야 한다 — 시장은 이미 이 기능을 당연시하고, 차별점은 오직 사내 볼트 근거와 절제된 통제다.**

**(a) 회의 중 AI 개입은 이미 반발을 겪었고, 승자의 교훈은 "통제·기본 절제"다.**
2026년 7월 MS Teams는 회의 중 AI(Copilot·Facilitator·Recap)에 대한 사용자 반발로 **회의 도중 끄는 토글**을 급히 추가했다. 즉 대기업조차 "AI가 회의에 끼어드는 것"에서 밀렸고, 시장이 요구한 건 더 똑똑한 개입이 아니라 **끌 수 있는 권한**이었다. 우리 설계의 기본 OFF·페르소나별 참견도·전역 상한·즉시 정지·관찰모드 우선은 이 교훈과 정확히 일치한다 — 이건 보수성이 아니라 시장 검증된 필수 조건이다.

**(b) "옆 멘트만으로 보완된다"는 사용자 직관은 학술적으로 뒷받침된다.**
CHI 2025 "Are We On Track?"(AI-assisted goal reflection during meetings)는 "지원 vs 방해" 딜레마를 정면으로 다룬다: AI 개입이 잦으면 참여·성찰을 해치고, 없으면 인지 과부하가 온다. 처방은 **"능동 토론 중엔 짧은 요약이 방해를 최소화, 지난 주제 재방문 땐 상세 정보"** — 우리의 앰비언트 옆 카드(짧은 문장·무음·실시간) vs 종료 후 finalize(상세·전량 검증) 역할 분담과 그대로 겹친다. 사용자가 말한 "옆 멘트가 보이는 것조차 도움"은 이 연구의 핵심 처방이다.

**(c) 데블스 애드버킷·페르소나 레드팀은 트렌드이자 검증된 패턴 — 단 대부분 비실시간이다.**
LLM 데블스 애드버킷(ACM IUI), 소수의견 증폭용 AI 중재(arxiv 2502.06251), PersonaTeaming(arxiv 2605.05682) 등 다관점·적대적 에이전트는 2025~2026 연구의 주류다. 실사용 도구(예: 투자심의용 Devil's Advocate)는 **모든 반론을 인용 가능한 1차 출처에 근거**시킨다 — 우리의 "근거 없으면 개입 안 함" 규칙과 동일. **냉철한 단서**: 이들 대부분은 async·턴제(브레인스토밍·심의) 환경이다. **실시간 라이브 회의에 적용하는 것이 검증 안 된 도약**이고, 그래서 M0 관찰모드로 실시간 오탐률을 먼저 재는 것이 정당하다.

**(d) 실시간 비용은 업계도 경계한다.**
2026 실측 자료에 따르면 Realtime API는 캐싱·툴출력 절삭 없이는 분당 $0.18~0.46까지 튄다(우리는 오디오 실시간이 아니라 전사 텍스트 위 LLM이라 더 싸지만, 상시 호출은 같은 함정). 이는 §5의 시간 기반 트리아지·§10의 전용 캡을 정당화한다.

**그래서 이 기능의 진짜 차별점(냉철하게)**: 실시간 요약·전사·개입은 이미 상품화된 레드오션이다. 우리가 남과 다른 유일한 지점은 **사내 볼트(Obsidian) 지식에 근거한 도메인 전문가·팩트체커 개입** — 범용 코파일럿이 못 하는 "우리 회사 노트엔 이렇게 적혀 있다"이다. v1의 자원을 여기(볼트 근거 앰비언트 개입)에 집중하고, 음성·범용 요약 같은 이미 흔한 기능은 뒤로 미루는 것이 자원 배분상 옳다.

## 19. UI/UX 상세 설계 (개발 착수 수준) `[소스 검증 — 현 프런트 구조 기준]`

프런트 스택: React + TypeScript + Vite, **Tailwind**(유틸리티 클래스), **framer-motion**(`AnimatePresence`/`motion.div`), **lucide-react** 아이콘. 신규 UI는 기존 관례를 그대로 따른다 — 새 디자인 시스템을 만들지 않는다. `[소스 검증: Recorder.tsx:1172, Settings.tsx:101]`

### 19.1 설계 원칙 — "흘깃 보고 넘길 수 있어야 한다"

개입 표면의 목표는 **glanceable**(흘깃 봄)이다. 읽지 않아도 회의가 굴러가고, 눈이 가면 도움이 된다. 근거: 회의 중 관련 노트를 띄우는 **emerald 스트립**이 이미 이 원칙으로 동작한다(가로 스크롤 h-9 바 + 펼침 상세, `Recorder.tsx:1265`). 페르소나 개입은 **그 바로 아래 "페르소나 레인"**을 하나 더 두는 것으로, 시각 언어를 공유하되 색으로 구분한다.

### 19.2 인미팅 레이아웃 (녹음 화면)

```
┌─ 헤더(zinc-900 다크바): 🎙 상태 · 타이머 · 비용/분 ──────────────┐
├─ [관련 노트 스트립]  emerald-50/70 · 가로 스크롤 · 기존 그대로 ──┤
├─ [페르소나 레인]  ✦ 신규 ✦  slate-50 · 가로 스크롤 카드 ────────┤   ← §19.3
│     🧭촉진자  📝서기  🎓도메인  … (참견도>0 · 개입 있을 때만 표시)   │
│     [마스터 토글: 페르소나 ●ON | 이번 세션 끔]  [지금 점검]         │
├─ 세션 설정(접이식) ─────────────────────────────────────────────┤
├─ 전사 패널(자동 스크롤) ───────────────────────────────────────┤
└─ 하단 컨트롤(녹음/정지) ───────────────────────────────────────┘
```

레인은 **개입이 0건이면 렌더하지 않는다**(빈 바가 공간을 먹지 않게). 첫 개입이 오면 `AnimatePresence`로 아래에서 밀려 나온다(기존 설정 패널과 같은 모션 관례).

### 19.3 페르소나 개입 카드

한 장 = WS `facilitation` 이벤트 1건. 가로 스크롤 칩(접힘) → 클릭 시 펼침(상세). 관련노트 카드의 `line-clamp-2`·`text-[11px]`·펼침 상세 패턴을 재사용.

**접힘(칩) 구조**

```
[😈] 악마의 변호인 · 초안        ← 아이콘 + 라벨 + draft 배지
"그 가정이 A 시나리오에서도…"    ← text 1줄 line-clamp-1
[⟲ 발화]  [✓ 확인]  [✕]         ← 발화 점프 · 확인(dismiss) · 닫기
```

**펼침 상세** — `text`(2~4문장) + `evidence[]`(📄노트/🌐웹, score, 링크) + `searched` 배지 + span 원문. 관련노트 펼침(`max-h-44 overflow-y-auto`)과 동일 컨테이너.

**페르소나별 색·아이콘 (위험 티어로 3색)** `[설계 판단]`

| 티어 | 페르소나 | 색(Tailwind) | 아이콘(lucide) |
|---|---|---|---|
| 저위험(정보) | 촉진자·서기·주니어 | `slate`/`sky` (border-sky-200 bg-sky-50) | Compass · NotebookPen · Baby |
| 중위험(관점) | 도메인·시니어·악마의 변호인 | `violet` (border-violet-200 bg-violet-50) | GraduationCap · ShieldAlert · Swords |
| 고위험(지적) | 팩트체커·비판자 | `amber`/`rose` (border-amber-200 bg-amber-50) | Search · AlertTriangle |

**배지**: `draft`(항상, 회색 "초안") / `searched`(팩트체커·도메인만: 🌐 "라이브 검증" 초록 vs ⚠ "미검증" 앰버 — §6) / 참견도(카드 우상단 작은 점 1~5, 디버그 뷰에서만).

### 19.4 상호작용

- **확인(✓)/닫기(✕)**: 카드 제거. 확인은 "봤다", 닫기는 "필요 없다"로 관찰 로그에 라벨 저장(향후 개인화·오탐 학습용).
- **발화 점프(⟲)**: 녹음 중에는 노트 이동을 막는 기존 정책(`Recorder.tsx:1344` "녹음 중에는 이동하지 않습니다")과 동일하게, **전사 패널의 해당 span으로 스크롤만** 한다(외부 열기 없음).
- **[지금 점검]**: 참견도 2(소극) 페르소나를 즉시 1회 돌려 그 시점 요약·놓침을 모아 보여준다(음성브리핑 트랙 A의 [지금 정리]와 같은 버튼 계열).
- **마스터 토글 / 이번 세션 끔**: 헤더에 항상 노출. 세션 중 끄면 그 세션에서 다시 안 켜진다(§4). **업계 교훈(§18 MS Teams)의 필수 요소 — 끄는 버튼이 항상 보여야 한다.**
- **개입 예산 소진**: 레인 끝에 "이번 회의 개입 12/12 — 이후는 기록만" 안내 칩.

### 19.5 상태·에러·빈 상태 (조용히 실패 금지 — 이 리포 반복 규칙)

| 상태 | 표시 |
|---|---|
| 비활성(enabled=false) | 레인·토글 자체를 렌더 안 함 |
| 활성·개입 0 | 레인 없음(빈 바 금지). 헤더 토글만 ●ON |

### 19.6 참견도 컨트롤 UI (설정)

### 20.2 PRD 대비 정정 6건

1. **관찰 로그는 후보만으로 부족하다 — 분모가 있어야 한다.** §15 는 "후보를 로깅해 precision 산출"이라고만 적었는데, 후보만 남기면 *기능이 안 돌았다 / 돌았지만 후보가 없었다 / 한도에 막혔다* 가 구분되지 않아 분모를 만들 수 없다. 시도 테이블(`facilitation_triage`)이 필수다.
2. **`triage_model` 은 "설정값"과 "과금될 모델"이 다르다.** `llm_client.chat` 의 model 은 GPT 전용이라 claude 계열은 `models.claude_model` 로 호출된다. §5 모델 배정표는 이 사실을 반영하지 않았다 → `facilitation.effective_triage_model()` 로 해석해 **추정·한도·기록·로그가 모두 실효 모델**을 쓴다. 남는 한계: `chat()` 의 벤더 폴백(gpt↔claude)은 감지할 수 없다(llm_client 확장 필요, 별건).
3. **§10 의 "세션 있으면 `db.add_session_cost()`" 는 이 기능에 적용하면 안 된다.** `wiki_core` 는 `web.backend` 를 import 하지 않는 구조이고, 무엇보다 `usage_log.month_to_date_spend()` 가 sessions 와 usage_log 를 **둘 다** 더하므로 양쪽에 적으면 이중 집계된다. → `spend_guard.record(kind=facilitation)` 만 쓰고, 세션별 금액은 `note` 규약(`spend_guard.session_note`)으로 `usage_log.session_spend()` 에서 되찾는다. 회의 상세 화면은 그 **실측값**을 표시한다(추정 아님).
4. **`estimate_session_cost(facilitation=True)` 는 사전 추정 경로에서만 켠다.** 켜야 하는 곳은 러닝 미터(`/api/cost/rates`)뿐이고, `sessions.cost_estimate` 를 **기록**하는 finalize 에서 켜면 3번과 같은 이중 집계가 된다. 회귀 테스트로 고정했다.
5. **창(window)은 트리아지 후 비워야 한다.** §5 는 "최근 창"만 적었는데, 2000자 창(≈발화 5분)을 비우지 않으면 같은 발화가 25초마다 최대 ~12회 재판정돼 분자가 부풀고 토큰이 헛돈다. → 마지막 1건만 문맥 다리로 남기고, 잔여 중복은 `span_hash` dedup 이 흡수(`repeats` 증가).
6. **미구현 설정을 설정 화면에 올리지 않는다.** `max_interventions_per_session`·`voice_enabled`·`web_search_enabled`·`web_search_interval` 은 §9 에 있으나 읽는 코드가 없어 스키마에서 내렸다(config.example.json 주석에만 유지). 해당 마일스톤에서 코드와 함께 올린다.

### 20.3 함께 고친 인접 결함(이 기능 밖)

## 부록 A — 이 PRD를 쓰며 정정한 판단

정직성을 위해 남긴다.

1. **"페르소나마다 모델을 붙이면 비용이 폭발한다"가 첫 우려였다.** 그런데 트리아지를 페르소나별로 나누지 않고 **1회 호출에 전 페르소나를 묶으면** 상시 호출 수는 페르소나 수와 무관해진다(세그먼트 창 수에만 비례). 상위 모델은 실제 개입 시에만 — 그래서 하이브리드 계층형이 성립한다.
2. **"참견도"를 단순 빈도 노브로 볼 뻔했다.** 실제로는 빈도 + **채널(로그→화면→알림음→음성)** + **롤아웃 단계**를 하나로 묶는 축이다. 특히 값 1(관찰)이 오탐률 실측 좌석이라는 점이 이 설계에서 위험을 지지 않고 근거를 쌓는 유일한 길이다.
3. **트랙 B(보류)를 그냥 되살리는 것으로 오해할 뻔했다.** 선행 PRD가 트랙 B를 보류한 이유(틀린 지적의 비대칭 비용)는 유효하다. 이 PRD는 그걸 무시하는 게 아니라, 대조표현·하드캡·관찰모드·오탐률 게이트로 **그 위험을 수치축 안에 가둔** 재설계다.
4. **(v0.2) "비용 가드는 이미 있으니 복제하면 된다"가 v0.1의 가장 큰 오판이었다.** `realtime.py`에 `spend_guard` 참조가 0건임을 감사로 확인했다 — 복제할 대상 자체가 무계량이었다. 실시간·자동 경로가 가드를 우회하는 건 이 리포의 반복된 실패 양상이고(git 로그 3건), 새 상시 경로는 그 함정에 가장 빠지기 쉽다. "직접 배선 + 테스트 고정"으로 다시 썼다.
5. **(v0.2) 실시간의 가치를 음성으로 착각했다.** 사용자 지적으로 바로잡았다 — 옆에 뜨는 무음 카드만으로 의견이 보완되는 것이 실시간의 본체이고, 이건 이미 작동하는 채널(`related_notes`) 위에 카드를 얹는 저위험 확장이다. 음성은 부가 채널일 뿐 가치의 중심이 아니다. CHI 2025 연구가 이 재정렬을 뒷받침한다.

   이벤트(`costUsd`, 같은 pricing 함수)에 실어 보내고 화면이 **실제 발생분만** 합산한다.
   추정이 아니라 실측이라는 점에서 §10 의 의도(표시=과금)에 더 맞다.
2. **confidence 임계는 페르소나별이 아니라 전역 1개다.** §20.4 는 "페르소나별 confidence
   임계(현재 Persona 에 없음)"를 M1 몫으로 적었지만, 실측 전에 8개 숫자를 지어내는 것은
   이 리포가 금지한 근거 없는 랭킹 휴리스틱이다. `facilitation.min_confidence`(기본 0.6)
   하나만 두고, 필터를 **파싱이 아니라 표시 단계**에 뒀다 — 모든 후보의 confidence 가
   로그에 남아야 나중에 분포를 보고 나눌 수 있다.
3. **참견도 설정 UI 가 M1 의 전제였다.** §19.6 은 이것을 UI 항목으로만 다뤘는데, 실제로는
   기능의 on/off 였다: M0 부터 쓰던 config.json 은 전원 참견도 1 이고 참견도는 설정 화면에
   없었으므로, 이 화면 없이는 M1 코드가 들어가도 화면에 아무것도 뜨지 않는다.
   목록·상한·실효값은 서버 레지스트리에서 받는다(`persona_level()` 을 모듈 함수로 승격) —
   프런트가 클램프를 새로 계산하면 "3으로 올렸는데 안 뜬다"가 된다.
4. **§19.4 의 확인/닫기 라벨은 '향후 개인화용'이 아니라 M2 게이트의 실측 채널이다.**
   §15 는 라벨링을 "종료 후 사람이 대조"로 뒀는데, 그 작업은 실무에서 하지 않게 되고
   그러면 게이트가 영구히 닫힌다. 회의 중 이미 누르는 버튼을 라벨로 쓴다
   (`facilitation_log.feedback`, 별도 테이블 금지 — purge 사이드카가 늘어난다).
   단, **'닫기'는 그대로 오탐이 아니다**('틀렸다'와 '맞지만 지금은 불필요하다'가 섞여
   있고, 라벨 가능한 분모는 화면에 뜬 개입뿐) — 리포트가 비율만 세고 판정하지 않는다.
5. **§19.4 의 [지금 점검]은 "참견도 2 페르소나를 즉시 1회 돌린다"가 아니다.** 버튼 한 번이
   새 LLM 호출을 만들면 사용자가 비용을 예측할 수 없다. → 이미 생성해 둔 대기분을
   방출만 한다(추가 과금 0). 새 판정은 다음 트리아지 주기에 자연히 돈다.

### 21.3 M1 기본값 (config.example.json)

저위험 4종(촉진자·서기·주니어·시니어)만 3(옆 카드), 중·고위험 4종은 1(관찰) 고정.
기능 자체는 여전히 **기본 꺼짐**(`facilitation.enabled=false`)이다.

### 21.4 M2 착수 전 남은 것

- **오탐률 실측** — 여전히 게이트다. 이제 두 경로로 모을 수 있다: 라이브 회의(참견도 3
  으로 카드를 띄우고 확인/닫기를 누른다) + `facilitation-report` 리플레이(지난 회의 확정
  전사). 리플레이 precision 은 조건이 유리해 **상한**이다.
- `summarizer` 페르소나(미결 #3 결정분) — **완료**. 아래 §21.5 참조.
- M2 범위: 위험 페르소나 개방 + `web_research` `searched=True` 게이트 + 라이브 웹검색
  배선(현재 개입 이벤트의 `searched` 는 항상 false).

### 21.5 중간 요약(summarizer) — 음성브리핑 트랙 A 를 합친 결과

음성브리핑 PRD 의 트랙 A(회의 중간 요약)를 별도 모듈(`midway_brief.py`)·별도 설정
섹션(`realtime.midway_brief.*`)·별도 WS 이벤트(`midway_brief`)로 만들지 않고, 이
오케스트레이터의 **주기 페르소나 1종**으로 합쳤다(그 PRD 미결 #3 결정). 그 PRD 문면과
달라진 점을 남긴다:

1. **설정 위치**: `realtime.midway_brief.*` → `facilitation.brief_period_sec` /
   `brief_min_new_chars` + 참견도 매트릭스의 `🧾 중간 요약` 행. 게이트가 두 벌이 되면
   "켰는데 안 나온다"의 원인이 두 곳으로 늘어난다.
2. **WS 이벤트**: 신설 `midway_brief` 대신 기존 `facilitation` 카드에 `kind="brief"` +
   `brief{points,decisions,actions,open_questions}`. 프런트 채널·모션·끄는 버튼·확인/닫기
   라벨을 그대로 재사용한다(신규 UI 위험 0).
3. **비용**: `pricing.facilitation_brief_cost()` 신설(입력 4k·출력 500 상한, `[미검증]`).
   개입과 같은 3관문 + 회의당 캡 예약/환불을 지난다. 단 **개입 예산은 소모하지 않는다** —
   주기 기반이라 횟수가 이미 시간으로 묶여 있고(트리아지와 같은 성질), 기회주의적 개입
   카드가 사용자가 기대하는 주기 요약을 굶기면 안 된다.
4. **트리아지와 분리**: `Persona.periodic=True` 이고 `personas.triage_personas()` 가
   트리아지 입력에서 제외한다. 요약이 후보로 잡히면 오탐률 분모가 오염되고 상시 프롬프트가
   길어진다. `report()` 도 `briefs` 를 `candidates` 와 따로 센다.
5. **참견도 1(관찰)에 '요약 기록만' 상태를 두지 않았다.** 요약은 판정 대상이 아니라 읽어야
   의미가 있는 산출물이라, 아무도 보지 않는 요약에 Tier 1 비용을 쓰지 않는다(예산 소진 시
   생성을 멈추는 것과 같은 이유). 2 이상에서만 생성한다.
6. **[지금 정리]는 [지금 점검]과 성질이 다르다.** 후자는 대기분 방출(과금 0), 전자는 새 요약
   1회(과금 발생). 그래서 최소 간격 20초·새 발화 없으면 거부·사유를 항상 화면에 돌려주고,
   버튼 툴팁에 비용이 든다는 사실을 적는다. 참견도 2 여도 눌렀을 때는 대기열이 아니라 바로
   보여준다(눌렀는데 안 뜨면 고장으로 읽힌다).
7. **입력은 '지난 정리 이후 발화 + 이전 요약 1개'**(FR-A2 그대로). 트리아지 창을 재사용하지
   않는다 — 그 창은 회차마다 비워지므로 요약이 마지막 25초만 보게 된다.

TTS(트랙 C)는 합치지 않았다 — 프런트 `lib/tts.ts` 몫이고 M3 게이트(되먹임 실측) 뒤다.

## 22. 개입의 "내용" 보강 + 산출물 보존 (2026-08-05) `[소스 검증]`

M1 은 "카드가 뜬다"까지였다. 사용자 요구는 **"관련 정보/의견 검증 · 필요 질문 제시 ·
이전 회의/사실과 다른 내용 체크가 STT 로 회의를 계속 분석하면서 뜬다"** 였고, 코드로
전 경로를 추적하니 **회의 후는 되고 회의 중은 재료가 없는** 비대칭이었다.

### 22.1 진단 — 무엇이 없었나

| 원하는 것 | 담당 | M1 상태 |
|---|---|---|
| 정보 검증 | 🔍 팩트체커 | `hard_cap=2` 로 화면에 못 나옴 + 웹 근거 미전달 |
| 의견 제시 | 😈 악마의 변호인 · 🎓 도메인 | 근거가 후보와 무관(세션 누적 상위 5) |
| 필요 질문 | 🧨 시니어 · 🐣 주니어 | 동작(같은 근거 문제) |
| 이전 회의와 다름 | 🧐 비판자 · 팩트체커 | **재료 0건** — 판정할 입력 자체가 없음 |

`decision_registry.json`·`action_registry.json`·지식그래프에 대한 실시간 경로의 참조가
**0건**이었다. 종료 후 경로(`meeting_workflow.build_meeting_context`)는 볼트·그래프·
지난 결정/액션·엔티티 겹침·웹을 모두 조립해 회의록을 쓰는데, 실시간은 페르소나 목록 +
주제 + 최근 발화가 프롬프트 입력의 전부였다.

### 22.2 결정 대장

1. **고위험 2종(팩트체커·비판자)의 `hard_cap` 2 → 3** (소유자 결정, §15 오탐률 실측
   게이트 **이전**). 사용자가 원한 기능의 담당이 정확히 이 둘인데 상한 2 로 잠가 두면
   설정에서 3 을 골라도 카드가 뜨지 않아 "켰는데 아무것도 안 나온다"가 된다.
   - **기본값은 그대로 1(관찰)** — 시드도 프리셋 3종도 올리지 않는다(회귀 테스트로 고정).
   - 3 을 고르면 설정 화면이 인라인 경고를 띄운다: 오탐률 실측 전이고, 카드의
     ✓확인/✕닫기가 그 실측 데이터가 된다.
   - 4·5(알림음·음성)는 미구현이라 여전히 잠겨 있다.
2. **이전 회의 재료를 트리아지·생성 둘 다에 주입**(둘 중 하나만 하면 "트리아지는
   아는데 생성은 모르는" 상태가 되어 근거 없는 개입이 나간다). 건수는
   `facilitation.context_decisions`/`context_actions`(기본 5, `[미검증]`).
3. **팩트체커 프롬프트의 "라이브 검색 근거 필수" 는 잘못된 쪽이었다.** 이 제품은
   내부 자료 우선(FR-10)이라 볼트에서 찾으면 웹을 아예 부르지 않는다 — 그 조건대로면
   팩트체커는 영구 침묵한다. 사내 노트·논문·지난 결정도 대조 근거로 인정하고, 웹
   근거의 유무는 카드의 `searched`(⚠ 미검증 배지)로 **구분해 보여준다**.
4. **개입 생성이 웹을 새로 부르지 않는다.** 이미 나간 결과만 읽는다 — 개입마다 유료
   검색을 더하면 회의당 비용이 예측 불가가 된다. 라이브 재검색은 M2 그대로.
5. **`searched` 는 이제 사실이다.** M1 에서는 상수 false 라 ⚠ 미검증 배지가 아무것도
   말하지 않았다(§21.4 의 "현재 항상 false" 항목 해소).

### 22.3 산출물 보존

- **중간 요약이 종료와 함께 사라졌다** — 화면 카드로만 존재했고 관찰 로그의 `span` 은
  500자 컷이라 복원 불가였다. → `briefs_markdown()` → `documents.brief` →
  회의 상세 **[중간 정리]** 탭. 회의록과 별도 문서다(정본 vs 시점별 스냅샷).
- **마지막 구간이 통째로 빠졌다** — 주기 600초라 25분 회의면 t=600 요약 1건뿐이다.
  → `finalize_brief()`(TRIGGER_BRIEF_FINAL). **주기 게이트만** 우회하고 mute·채널·
  참견도·내용 게이트·비용 3관문은 그대로. 취소 경로에서는 부르지 않는다.
- **A절 타임라인 실측**: 판정은 **보정 전 조각**으로 이뤄지고 종료 후 재판정은 하지
  않는다(§15 가 의도적으로 배제 — 사람 대조). 다만 보정이 교체를 포기하는 경로가
  3개(1초 미만·무음·반복 과다) 있어 조각이 최종본과 같은 경우가 있다 →
  `facilitation_log.revised` + `mark_revised_spans()` 로 구분하고 `report()` 가
  `provisional_unrevised` 를 따로 센다. **표시 전에는 두 수치가 같다**(모르는 것을
  아는 척하지 않는다).

### 22.4 함께 고친 인접 결함

- 관련 노트 바에 [이번 회의 끔]이 없었다 → 추가하되 **서버 검색·웹 보완 과금까지**
  멈춘다(페르소나 mute 와 같은 계약). 볼트만 멈추면 비싼 쪽(웹)만 남는다.
- 레인에 **"소리 없음"** 상시 표시 — 참견도 4·5 는 미구현이고 리포에 소리 재생 코드가
  0건이다. "소리 어떻게 끄냐"의 답은 "끌 소리가 없다"이고 화면이 그걸 말해야 한다.
- 도움말에 "녹음 중 화면에 뜨는 것 · 끄는 법" 절.

### 22.5 M2 착수 전 남은 것

- **오탐률 실측** — 이제 고위험 2종도 화면에 열 수 있으므로 라벨이 실제로 모인다.
- 라이브 웹 재검색(개입 시점 검색)은 여전히 M2. 지금은 "이미 나간 결과 읽기"다.
- 지식그래프는 아직 실시간 경로에 주입하지 않았다(registry 만). 그래프는 조회 비용이
  registry(JSON 1회 읽기)와 달라 실측 후 결정한다.
