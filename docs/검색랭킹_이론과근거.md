# 실시간 관련노트 검색 — 랭킹 이론과 실측 근거

작성 2026-07-29 · 대상 코드 `wiki_core/realtime_search.py`, `wiki_core/vault_indexer.py`
재현 스크립트 `scripts/bench_realtime_ranking.py` · 측정 볼트 **472노트 / 3,744섹션**

> **측정 이력 주의.** 이 문서의 첫 판(같은 날 오전)은 **낡은 인덱스(802노트)** 로 측정했다.
> 그 인덱스는 그림자 사본(`*.txt.md` 등)을 걸러내는 필터가 들어오기 전에 빌드된 것이어서
> 중복 노트가 대량 섞여 있었다. `reindex` 후 472노트로 재측정하니 **절대 수치가 크게 오르고
> 일부 결론이 뒤집혔다**(§5.0). 아래 수치는 전부 재측정본(472노트)이며, 두 인덱스에서
> 모두 살아남은 결론과 그렇지 않은 결론을 구분해 적었다.

이 문서의 목적은 **랭킹 결정을 "느낌"에서 떼어내는 것**이다. 실시간 관련노트 검색은
"섹션을 먼저 볼까", "논문 폴더를 우대할까", "쿼리를 몇 자로 자를까" 같은 선택이 많고,
전부 그럴듯해 보인다. 실제로 이 프로젝트에서도 그럴듯한 휴리스틱 2개(섹션 인덱스를
랭킹에 융합, 논문 폴더 점수 1.2배)를 넣었다가 **실측에서 반박돼 제거했다**(§5).
그래서 여기에는 ① 어떤 신호를 왜 쓰는지, ② 왜 그 방식으로 합치는지, ③ 숫자가 무엇을
말했는지, ④ 어떤 조건에서 이 결론이 뒤집히는지를 함께 적는다.

---

## 1. 문제 정의

회의 중 발화 세그먼트(수 초~수십 초 분량의 텍스트 한 조각)가 확정될 때마다, 사내 노트
폴더에서 관련 자료를 찾아 화면에 보여주고 종료 후 근거로 남긴다. 제약이 랭킹 설계를
지배한다.

| 제약 | 랭킹에 주는 영향 |
|---|---|
| 전사 스트림 보호(논블로킹·예외 무전파) | 쿼리당 수십 ms 급 로컬 계산 + 실패 시 조용한 폴백 |
| 화면 표시 3개 | **recall@3** 이 사실상의 목표 지표. recall@10 은 의미가 적다 |
| 근거 추적(FR-3) | 노트만이 아니라 **어느 섹션**인지까지 있어야 한다 |
| 내부자료 우선(FR-11) | 로컬 논문/이론 노트가 후보에서 탈락하지 않아야 한다 |
| 저비용 | 쿼리 임베딩 1회/검색, 노트 임베딩은 사전 계산 재사용 |
| 오프라인 가능성 | 임베딩 실패 시 TF-IDF 단독으로 계속 동작해야 한다 |

핵심: **정답 라벨이 없다.** 그래서 §4에서 합성 쿼리로 프록시 지표를 만든다.

## 2. 쓰는 신호 3종 (코드 대조)

### 2.1 어휘 신호 — TF-IDF (`vault_indexer.py`)

- 토큰화(`_tokenize_plain`): 한국어는 **bigram + trigram**, 영어/숫자는 소문자 단어
  (불용어 제외). 형태소 분석기 의존을 피하려는 선택 — 조사·어미 변화에 강한 대신
  어휘 사전이 커진다(이 볼트 84,477 term).
- `tf(t,d) = count(t,d) / |d|` (`_compute_tf`) — **길이 정규화된 tf**.
- `idf(t) = ln(1 + N/(1+df(t)))` — N = 노트 수.
- 인덱스에 저장할 때 이미 `tf·idf` 를 곱해 노트당 상위 200개(섹션당 50개) term 만 남긴다
  (인덱스 크기 절약, `build()`).
- 질의 시 `search()` 는 저장값에 `idf` 를 **한 번 더** 곱한다 → 실효 가중은 `tf·idf²`.
  교과서 TF-IDF 와 다른 지점이라 실측으로 확인했다: 이중 idf 를 제거하면 MRR
  0.664 → 0.648 로 오히려 소폭 나빴다(§5, `single_idf` 변이). **차이는 n=24 에서
  유의하지 않으므로 "바꿀 근거가 없다"가 결론**이고, 문서화만 해 둔다(희귀어를 더 강하게
  가중하는 효과가 이 볼트의 고유명사 위주 질의와 맞는 것으로 보인다).

**섹션 점수의 함정.** `tf` 가 길이 정규화되어 있으므로, 같은 단어 1회 등장이 2,000토큰
노트에서는 0.0005, 5토큰짜리 짧은 섹션에서는 0.2 다. 즉 **섹션 점수는 짧은 섹션에서
구조적으로 과대평가**된다. 헤딩만 나열된 목차 섹션이 상위로 올라오는 이유이고,
섹션 점수를 노트 점수와 같은 축에서 비교하면 안 되는 이유다.

### 2.2 의미 신호 — 임베딩 코사인

- 모델 `text-embedding-3-small`, 차원 **256**(Matryoshka 축소 — 1536 원본 대비 인덱스
  크기·계산량을 6배 줄이면서 성능 손실은 작다는 공급자 주장에 의존).
- 벡터는 L2 정규화 저장 → 내적이 곧 코사인(`_dot`, `_l2_normalize`).
- `embedding_min_cosine = 0.25` 미만은 버린다(노이즈 컷). 0.25 는 공급자·경험적 관례이며
  이 볼트에서 별도 튜닝하지 않았다 — **재검증 대상**(§8).
- 전량 브루트포스: 802벡터 × 256차원 ≈ 20만 곱셈 → ms 급. ANN 불필요(§7).
- 쿼리 벡터는 캐시(`_query_vec_cache`)되지만 **API 왕복이 지연의 최대 항목**
  (중앙값 372ms, §6). 로컬 계산(37ms)의 10배다.

### 2.3 위치 신호 — 섹션(heading) 인덱스

노트를 `#` 헤딩 단위로 쪼개 섹션별 tf 를 갖는다(`_parse_sections`,
`section_index_enabled`). PageIndex 의 트리 아이디어를 얕게 구현한 형태다.
**용도는 랭킹이 아니라 "노트 안 어디가 근거인가"** — §5 에서 실측으로 확정된 역할이다.

## 3. 왜 순위 융합(RRF)인가

두 신호를 합치는 방법은 점수 결합과 순위 결합이 있다.

**점수 합은 성립하지 않는다.** TF-IDF 점수는 상한이 없고 문서·질의마다 스케일이 다르다
(이 볼트 실측 범위 0.1~11). 코사인은 [-1, 1]. 섹션 TF-IDF 는 §2.1 대로 짧은 섹션에서
부풀려진다. 서로 다른 축의 값을 더하면 **가장 스케일이 큰 신호가 사실상 단독 결정**을
한다. 초기 측정에서 정규화 없는 점수 합은 MRR 0.528 로 가장 나빴다(RRF 0.648 대비).
리스트별 최대값 정규화(min-max 류)는 나아지지만, 정규화 상수가 질의마다 흔들려
재현성이 떨어진다.

**RRF(Reciprocal Rank Fusion, Cormack et al. 2009)** 는 점수를 버리고 순위만 쓴다.

```
score(d) = Σ_r  1 / (k + rank_r(d))          k = 60
```

- 스케일 불변 — 서로 비교 불가한 신호를 합치는 데 이론적으로 안전하다.
- `k=60` 은 원 논문의 표준값으로, 상위 순위의 지배력을 완화한다(1위 대 2위 차이가
  1/61 대 1/62 로 작다). 이 볼트에서 k 를 별도 탐색하지는 않았다 — **재검증 대상**.
- 부작용: 점수 정보를 버리므로 "1위가 압도적으로 관련" 같은 신호가 사라지고, **동점이
  흔해진다**. 그래서 정렬은 안정(stable)해야 하고, 동점 처리 규칙을 명시해야 한다.
  현행 구현은 후보 삽입 순서를 유지하고 동점이면 논문 노트를 앞세운다.

`vault_indexer.search()` 는 TF-IDF 랭킹과 임베딩 랭킹을 RRF 로 융합하고
(`_rrf_fuse`), 실시간 경로는 그렇게 얻은 노트 랭킹의 **순위**를 다시
`1/(60+rank+1)` 로 환산해 `rank_score` 로 쓴다.

## 4. 측정 방법 (그리고 이 측정이 못 재는 것)

정답 라벨이 없으므로 **합성 쿼리**를 쓴다.

1. 볼트 노트에서 섹션이 2개 이상인 노트를 무작위(고정 seed) 추출.
2. 그중 가장 긴 섹션 본문을 정리(프론트매터·헤딩·코드블록 제거)해 앞부분에서
   180자를 잘라 **"발화"** 로 삼는다.
3. 정답 = (그 노트, 그 섹션 heading) 쌍.

지표:

| 지표 | 뜻 | 왜 보는가 |
|---|---|---|
| recall@1 / **recall@3** | 정답 노트가 1위 / 상위 3위 안 | 화면에 3개만 보이므로 R@3 이 실사용 지표 |
| MRR@10 | 정답의 역순위 평균 | 순위 개선을 연속적으로 본다 |
| **heading@3** | 정답 노트를 회수한 건 중, 돌려준 섹션이 정답 섹션인 비율 | 섹션 인덱스의 **본래 목적**을 재는 지표 |
| ms | 쿼리당 지연 중앙값 | 실시간 제약 |

**이 측정의 한계(중요).**

- 쿼리가 노트 본문에서 그대로 나왔으므로 **어휘 겹침이 실제 발화보다 크다** → 절대
  수치는 낙관적. 그리고 이 편향은 **구조적으로 TF-IDF 에 유리하고 임베딩에 불리**하다.
  실제 발화는 구어·요약·환언(paraphrase)이라 어휘가 어긋나는데, 그 상황이야말로 의미
  검색이 필요한 지점이다. 따라서 이 벤치마크로 **"임베딩이 쓸모없다"는 결론을 내릴 수는
  없다**(§5.5) — 환언 기반 평가셋이 있어야 답할 수 있는 질문이다.
- **정답을 1건으로 가정**한다. 실제로는 여러 노트가 모두 관련일 수 있고, 그 경우 이
  지표는 "다른 좋은 노트를 올린 랭킹"을 부당하게 감점한다.
- n=24 는 작다. **R@3 한 칸 차이 = 약 0.04** 이므로 0.04 이내 차이는 노이즈로 봐야 한다.
- 단일 볼트(한국어 중심, 양자컴퓨팅·AI 도메인)의 결과다.
- STT 오인식·화자 혼선이 없는 깨끗한 텍스트다 — 실제 실시간 입력은 더 지저분하다.

그래서 이 문서의 주장은 전부 **"이 볼트·이 프록시에서 이랬다"** 로 한정된다. 반대로,
**큰 차이(0.08 이상)와 지연 차이(수십~수백 ms)** 는 이 한계에도 살아남는 신호로 본다.

## 5. 결과 — 무엇이 반박됐나

쿼리 24건, 180자, 임베딩 ON, **472노트 인덱스**. `python scripts/bench_realtime_ranking.py --n 24`

| 변이 | R@1 | **R@3** | MRR@10 | **heading@3** | 논문/쿼리 | 로컬 ms |
|---|---|---|---|---|---|---|
| **shipped** 노트RRF + 논문보강 + 후보내 섹션 위치특정 | **.88** | .96 | **.920** | .87 | 2.12 | **61** |
| section_arm + 논문 1.2배 *(첫 구현, 폐기)* | .75 | 1.00 | .861 | .83 | 2.46 | 327 |
| section_arm (가산 없음) | .79 | .96 | .876 | .83 | 2.21 | 327 |
| section_arm (섹션 가중 0.5) | .83 | 1.00 | .903 | .83 | 2.00 | ~330 |
| notes_only *(구버전 경로)* | .88 | .96 | .920 | **0.00** | 2.12 | 23 |
| shipped + 논문 1.2배 | .62 | .71 | .708 | 1.00 | 3.00 | 88 |
| single_idf (이중 idf 제거) | .83 | 1.00 | .903 | .88 | 2.25 | 74 |

**5.0 인덱스가 바뀌면 절대 수치는 통째로 바뀐다.**
같은 코드·같은 방법으로 낡은 802노트 인덱스에서는 shipped R@3 = .75 였는데, 그림자
사본을 제거한 472노트 인덱스에서는 **.96** 이다. 원인은 랭킹이 아니라 **데이터 위생**:
중복 사본이 상위를 잠식하고 있었다. → 교훈 두 가지. ① 랭킹을 손보기 전에 인덱스가
최신·정상인지 확인할 것(`reindex`). ② 절대 수치를 다른 볼트·다른 시점과 비교하지 말 것.
아래 결론들은 **두 인덱스에서 모두 성립했는지**를 함께 표시한다.

**5.1 논문 폴더 점수 가산(1.2배)은 해롭다 — 제거했다. [두 인덱스 모두 ✔]**
802노트: MRR .664→**.575**. 472노트: .920→**.708**, R@3 .96→**.71**. 폴더 소속은
**관련도의 증거가 아니다**. 가산은 목표(논문 노출)에는 작동했지만(논문/쿼리 2.12→3.00)
관련 없는 논문이 관련 있는 회의 노트를 밀어냈다. → 폴더 우대는 **동점 tie-break** 로만
하고, 노출 보장은 "논문 폴더 한정 검색을 별도 arm 으로 돌려 후보 풀에 넣는" 방식으로
옮겼다(FR-11 은 그대로 충족). **이 문서에서 가장 강한 신호**(효과 크기 0.2 이상).

**5.2 볼트 전체 섹션 검색을 랭킹 arm 으로 쓸 이유가 없다. [부분 ✔ — 근거가 바뀜]**
- 802노트에서는 회수 자체가 나빠졌다(R@3 .75→.71).
- 472노트에서는 회수 차이가 사라졌다: section_arm 계열 R@3 .96~1.00 vs shipped .96
  (**1건 = 0.04, 노이즈 범위**), MRR 은 shipped 가 .920 으로 오히려 가장 높다.
- 따라서 지금의 근거는 "회수가 나빠진다"가 아니라 **지연(61ms → 327ms, 5배)** 과
  **heading 정확도(.87 vs .83)** 다. 같은 정보를 5배 비싸게 얻을 이유가 없다.
- 정직하게: 만약 지연 예산이 넉넉하고 R@3 1.00 이 꼭 필요하다면 `section_arm(가중 0.5)`
  는 재검토할 가치가 있다. 다만 그 우위는 현재 **쿼리 1건 차이**로, 이 표본에서는
  구분할 수 없다.

**5.3 그러나 섹션 신호는 버리면 안 된다. [두 인덱스 모두 ✔]**
`notes_only` 는 노트 회수가 shipped 와 **완전히 동일**(.88/.96/.920)하지만
**heading@3 = 0** — 근거를 짚지 못한다(FR-3 실패). 그래서 섹션은 **랭킹에서 빼고, 이미
뽑은 후보 노트 안에서만** 채점하도록 옮겼다(`VaultIndexer.sections_in_notes()`).
결과: 노트 회수는 notes_only 와 같고 heading 정확도 .87, 지연은 +38ms(그중 섹션 채점은
0.6ms).

> 요약하면 **역할 분리**다 — 노트 인덱스는 *무엇을* 보여줄지, 섹션 인덱스는 *어디를*
> 근거로 댈지 정한다. 첫 구현은 이 둘을 한 축에 섞어 양쪽을 다 나쁘게 만들었다.

**5.4 쿼리 길이는 길수록 좋다(비용·현실 한도 안에서). [두 인덱스 모두 ✔]**

| 쿼리 | R@1 | R@3 | MRR | (802노트에서) R@3 |
|---|---|---|---|---|
| 60자 *(최초 구현)* | .71 | .79 | .768 | .50 |
| **180자 (현행)** | .88 | .96 | .920 | .75 |
| 400자 | .88 | 1.00 | .938 | .88 |

60→180 은 두 인덱스에서 각각 R@3 +0.17 / +0.25 로 노이즈를 압도한다. 400자가 더 좋지만
**단일 발화 세그먼트가 400자에 도달하기 어렵다**(2-pass 보정 문장이 보통 수십~150자).
→ Phase 1 개선안: 최근 2~3개 세그먼트를 이어붙여 쿼리로 쓰기(§8).

**5.5 교차언어(FR-13) — 이 벤치마크로는 임베딩의 이득을 확인할 수 없다. [결론 뒤집힘 ⚠]**
쿼리에서 한쪽 언어 토큰만 남겨 측정(472노트).

| 쿼리 | R@1 | R@3 | MRR | (802노트) MRR |
|---|---|---|---|---|
| 한국어만, 임베딩 ON | .92 | .96 | .937 | .851 |
| 한국어만, 임베딩 OFF | .96 | .96 | **.965** | .745 |
| 영어만, 임베딩 ON | **.50** | .62 | .564 | .339 |
| 영어만, 임베딩 OFF | .42 | **.67** | .564 | .269 |

- 802노트(중복 포함) 인덱스에서는 임베딩이 확실히 도움이 됐다(ko MRR +0.11, en +0.07).
  **그 이득의 상당 부분은 중복 사본 사이의 판별이었을 가능성이 크다** — 중복을 제거한
  472노트에서는 ko 는 OFF 가 소폭 높고(.965 vs .937) en 은 MRR 동일(.564)이다.
- 즉 **이 측정으로는 "임베딩이 실시간 검색 품질을 올린다"를 지지할 수 없다.** 다만 §4 의
  편향을 기억할 것: 합성 쿼리는 노트 본문 축자 발췌라 어휘 매칭에 절대적으로 유리하고,
  의미 검색이 필요한 상황(구어·환언·다른 용어)을 아예 재지 못한다. **"이득 없음"이 아니라
  "이 방법으로는 답할 수 없음"** 이 정확한 결론이다.
- 확실한 사실은 하나: **영어 쿼리(R@3 .62)가 한국어(.96)보다 뚜렷하게 나쁘다.** 한국어
  중심 볼트에서 영어 발화의 교차언어 회수는 여전히 약점이다.
- 실무 판단: 임베딩 경로는 **켠 채로 유지**한다(실패 시 TF-IDF 폴백이 있고, 비용은 쿼리당
  1회·수십 토큰). 다만 "임베딩 덕분에 잘 된다"고 말하지는 않는다. 판정하려면 실제 회의
  전사에서 사람이 정답을 매긴 **환언 평가셋**이 필요하다(§8 최우선 항목).

**5.6 이중 idf 는 건드리지 않는다. [두 인덱스 모두 노이즈 범위]**
제거 시 802노트 MRR .664→.648, 472노트 .920→.903 — 두 번 다 소폭 하락이지만 노이즈
범위다. 바꿀 근거가 없고, `search()` 는 위키 Q&A·사실검증도 공유하므로 변경 위험이
이득보다 크다.

## 7. 규모 — ANN·PageIndex 가 필요해지는 지점

측정 시점 볼트: **노트 472 · 섹션 3,744(노트당 7.9) · 벡터 472×256 · 사전 47,198 term**.
(PRD 는 108노트를 가정했는데 실제는 4배 이상이다. 낡은 인덱스에서는 802노트·12,140섹션으로
보였지만 그중 상당수가 그림자 사본이었다 — §5.0.)

- **브루트포스 코사인** 비용 = 노트 수 × 차원 = 12만 곱셈 ≈ 수 ms. 10,000노트에서도
  256만 곱셈으로 수십 ms 수준 → **ANN(turbovec/faiss)은 여전히 불필요**하다.
- 병목은 벡터 검색이 아니라 ① 임베딩 API 왕복(286ms), ② 전체 섹션 스캔(159ms, 제거함),
  ③ TF-IDF 사전 크기(47k term)다.
- 따라서 Phase 1 전환 트리거는 "노트 수"가 아니라 다음 중 하나가 실제로 발생할 때다:
  - 로컬 계산이 쿼리당 200ms 를 넘는다(대략 노트 5,000+ 또는 섹션 위치특정 후보 100+).
  - 완전 오프라인(에어갭) 요구 → 로컬 임베딩(model2vec 등)이 **Phase 0 필수**가 된다.
  - 교차언어 품질이 사용 불가 수준으로 문제가 된다 → 다국어 임베딩 교체(§5.5).
  - 긴 보고서에서 "섹션 트리 요약"이 필요해진다 → PageIndex 식 노드 요약(FR-7/8).

## 9. 재현 방법

```powershell
python run_meeting.py reindex                     # 인덱스 + 임베딩 빌드
python scripts/bench_realtime_ranking.py --n 24   # 표의 수치 재생성
python scripts/bench_realtime_ranking.py --no-embed --n 40   # API 비용 0(TF-IDF만)
```

- **먼저 `reindex` 를 할 것.** 낡은 인덱스로 재면 숫자가 통째로 달라진다(§5.0). 인덱스
  저장이 `WinError 32`(파일 점유)로 실패하면 웹 서버·워처를 끄고 다시 실행한다 — 실패
  시에도 `.tmp` 파일만 남고 기존 인덱스는 그대로여서 조용히 낡은 상태가 유지된다.
- 비용: 쿼리 1건당 임베딩 1회(약 100토큰) — 24건이면 $0.001 미만.
- 스크립트 마지막의 **구현 일치(top5)** 는 벤치의 랭킹 재현과 실제
  `RealtimeVaultSearcher._search_index()` 가 같은 순위를 내는지 검사한다. 여기서
  불일치가 나면 **문서의 수치가 아니라 벤치가 낡은 것**이니 먼저 그걸 고쳐야 한다.
  (2026-07-29 기준 24/24 일치)
- 볼트가 다르면 절대 수치는 당연히 달라진다. 판단은 항상 **변이 간 상대 비교**로.
